### 值得保留 — CargoManifest 真正关闭了 ghost-unloading

`Sim.gd:3989-4016` 的 arrival 只追加 manifest + world receipt；`4020-4038` 选择当前可整单卸下的最早 manifest；`4042-4072` 重新核对工人、node、容量、余额后执行 pay→stock→cargo complete→receipt。候选签发还把 exact manifest/node/duration 绑定进 option；focused fixture 覆盖空港、强塞旧 option、stale intent、余额/容量变化、被抢单、跨班、mid-use save/load 和 chain mutation。

这条链比早上的“有个叫卸货的 action 并发工资”高一个架构层级。货船又只是 `cargo_manifests + order + carriers[]` 的纯 View 投影，不创建第二 lifecycle/nav/save authority，正确避开了 festival-style dynamic object 的 save/load 导航漂移。

但“atomic”当前只能解释为**单线程、无 await、同一函数块内顺序提交**：代码先 `transfer()`，后 `_stock_move()`；若后者意外返回非整单，只 `push_error` 并返回 0，钱不会回滚。今天 preflight 与同步状态使该分支很难触发，但异步、多镇或 hook 一旦介入就会形成钱货脱钩。未来接口应是一个可预演、可一次提交、带 txid 的账本事务，或至少有故障注入测试证明任一步失败全状态回滚。

### P1 — manifest/order 是短测可用、长局与多镇不可用的数据结构

每次到港都把 id 追加到 `cargo_manifest_order`；完成后记录永久保留。`_first_unloadable_manifest()` 每次候选查询从历史开头扫，`WorldView.carrier_projections_for()` 又会按 route 在绘制时扫完整历史。60 天只有几十单，问题尚不显；长存档、多货、多路线、多镇会变成 O(routes × history) 的逐帧/逐候选成本，并让 save/digest 永久膨胀。

在第二货物前应落：

- `ready_queue_by_node_route` 作为权威索引；
- complete manifest 的确定性归档/压缩水位；
- 保存版本与旧档迁移；
- queue/index 与 canonical ledger 的重建等价测试；
- 10 年模拟下 state bytes、candidate time 与 View time 的上界门。

### P0（存档兼容）— 新权威状态仍沿用 schema 1，旧档会被静默当成新档

候选新增了 `cargo_manifests`、`cargo_manifest_order`、`core_population`、production-pool 等脚本状态，但 `Sim.gd:1321` 仍是 `SAVE_SCHEMA := 1`。`load_game()` 在 `1389-1408` 只遍历存档中已有 key 执行 `set()`，不会先把所有新字段重置到由旧档可推导的值，也没有 schema-1 内部迁移。

结果是 pre-P1 的 schema-1 存档仍被接受：fresh instance 会保留新变量的错误默认值（例如 `core_population=0`）；若同一 Sim 实例先运行过新局再载旧档，旧档缺失字段还可能保留 load 前的 manifest/人口状态。现有测试只证 same-version pending/mid-use roundtrip，没有 frozen pre-P1 save fixture。

合入前必须二选一：

1. bump schema 并明确拒载旧档；或
2. 加可审计 migration，先构造完整 clean defaults，再从旧 state 推导新字段，并用 committed 旧档 fixture 证明 migrate→save→reload 等价。

不能继续用“schema 相同”暗示兼容。

### P1 — P1-d 关闭了规模 #46 空集，但“人口权威”仍跨域泄漏

`d0c8cba` 的 P1-d 是真实增量：N>12 只有 exact bool `scale_floor=true` 的 lane 可出口；保护 floor 按 `ceil(authored_floor × prod_pool_num / prod_pool_den)` 缩放，batch/cadence/price 保持固定物理航线吞吐。core 15/23/59 的 focused teeth、odd-floor 取整、余额/地板/revenue/flag/N<base/N12/orphan/mismatch 均有测试；摘要网格报告 N16/N24/N60 每个 seed 都有 import/export provider，#44/#45/#46 满绿，#40 仅保留既知软红。

但它把“真实人口是多少”绑定到 production scaling ratio。资源卡自己承认：若 production-scale ablation 或 malformed scale data 让 ratio 留在 1，即使实际 agent >12，也会走 N12 floor=36。人口身份与生产倍率本应是两个 domain；应由独立 `core_population/base_core_population` 决定规模，再由 supply policy 决定是否/如何缩池。

`export_pair_scan` 共用可减少 provider/invariant 漂移，却形成 common-mode：它过滤掉 pay 与 stock 之间的无关事件，并把这种 interleave 判合法。因此 #46 证明的是 filtered pay/export 配对，不是全 event-log 不可穿插的事务原子性。下一版应用共同 txid/manifest id 绑定钱货，而不是继续依赖相邻/过滤序列。

### P1 — affiliate 有 total/core 工具，但还没有 first-class membership 模型

候选新增 `scale_population_plan()` 与 Harness 的 total/core 口径，这是对“`--agents 60` 实际 61”问题的正确修复方向。然而 shipping/CI 仍存在 legacy-core 调用：前一 PR run 的 scale arm 明确打印 `requested=16, core=16, total=17`。权威产品门还没有全部迁移到 total semantics。

更本质地，`Sim.gd:971-981` 先按 core 冻结 production/work-pull，再 append Tao；Tao 随后是完整 needs、消费、社交、选举与钱包 agent。初始化顺序正在同时表达 capacity、consumer、voter、reputation、survival 等多个 membership 轴。Tao 又在 rumor/private-secret seed loop 之后才加入，因此没有 self-owned seed secret；“fully integrated outsider”不是事实。

`p1a_affiliate_test` 只证明 seed1×20d 曾发生社交且 needs 没跌穿极低阈值，不抓最后 10 天、最长 zero-candidate 段或 social 吸收态。应补 Tao-specific held-out/tail liveness，并落显式能力：

```text
Membership {
  town_id, counts_for_capacity, consumes_local_supply,
  voter_scope, reputation_scope, survival_scope,

```

在这之前，affiliate 可以作为实验角色保留，但不能被当成未来多镇人口抽象的最终形式。

### P1 — 多镇、旅行与 page swap 仍没有实现增量

候选仍是单例 `world`、`town_stock`、全局 agents/blocked；没有 `TownState`、`TransitState`、town-scoped stock/jobs/knowledge，也没有 traveler social domain、第二镇或 state-driven hot/cold swap。当前 CargoManifest 是未来跨镇账本的好 seam，但尚未把 origin/destination domain 变成可执行隔离边界。

不能从“东海来一船货”外推成区域贸易，也不能从纯 View carrier 外推成旅行换页。正确顺序仍是先把单镇港口纵切做完，再用同一 manifest/txid 扩成两个 domain 的负对照。

另一个 future-proof tooth：manifest id 当前是 `manifest_<route>_<day>_<lane-index>`，在单 Sim/单镇内唯一；若两个镇复用同 route/day/lane 并合入区域 ledger 会直接碰撞。扩域前必须把 destination town/domain（最好再加 shipment sequence）纳入 authority key，而不是事后在 page-swap 合并存档时补救。
