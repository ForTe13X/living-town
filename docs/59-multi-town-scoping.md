# 59 · 多镇 / 区域 / 运输 —— 立项前的界定（**这不是计划，是"要不要立项"的判断材料**）

> 提出者：用户，2026-07-31。原话要点：**多个小镇、居民可在区域内往来、各镇有互补产业、
> 以此缓解经济设计压力；并引入 export/import，需要运输设计，既运货也让人流动多样化。**
> 前置：docs/41 §0.5（规模能力矩阵，**今天刚定的**）、docs/54 / docs/57 / docs/58 三份规模实测、
> M1 `630e40d` 与 M2 `d7f4ac4` 的回执。

## 〇、先把这个点子最强的版本说出来——**它可能不是经济特性**

用户给的理由是"缓解经济设计压力"。**这个理由成立，但它不是这个点子最强的部分**，
而且单看这一条，多镇是一条很绕的路（见 §二）。

**更强的版本**：一个**在两镇之间运货的人，同时在运消息**。
他在 A 镇听到的事，几天后出现在 B 镇；B 镇的人对 A 镇某人的看法，是**经由一个可追责的中间人**传过去的。
⇒ **这是社会涌现，不是经济模拟。** 而"确定性社会底座"正是本项目写在 README 里的卖点，
**经济精确模拟明确不是**（§0.5 的决定就建立在这个区分上）。

⇒ **建议的立项理由改成："给谣言/声誉/信念增加一条有延迟、有载体、可追责的跨镇通道。"**
经济互补是**附带收益**，不是主诉。这个改写不是文字游戏——它决定了先做哪一半（见 §四）。

## 一、它撞上的三件今天刚定的事

### ① §0.5 的"capacity"问题会**原样复发**

外部评审刚教过我们：`红线 #3「最多 60 居民」`同时可以读成 entity capacity 与 simulation capacity，
而**没写清楚**是那两波返工的根因。多镇立刻把同一个问题提高一维：

- **60 是"一个镇 60 人"还是"整个区域 60 人"？**
- 三个镇各 60 人 = 180 个 agent ⇒ **红线 #3 的性能目标要重新量**（M2 明说 N>24 一格都没测过）。
- 若是"区域共 60 人"，那每镇 20 人 ⇒ **正好落在 M2 刚修的那个 #01 高发区间 N∈[18,24]**。

⇒ **立项前必须先把这一行写进 §0.5**，否则会重演"失败还是超范围分不清"。

### ② 红线 #1（确定性 + 逐字节回放）的面积会显著变大

今天所有的门都建立在"单一世界、单一 `tick_no`、单一 `event_log`"上。多镇引入：
跨镇实体转移、旅途中的 agent 属于谁、镇 A 的 tick 与镇 B 的 tick 如何定序。
**这些都不是不可做，但每一条都会变成新的金标面**，而本 session 反复证明：
**新的状态面 = 新的、没人守的盲区**。

### ③ §0.5 刚定的"双尺度"要跨镇再判一次

我们刚决定"微观算人、宏观估产业"。跨镇贸易是**微观**（一车货、一个赶车的人）
还是**宏观**（两镇之间一个供给指数）？**两种都说得通，而选错会把刚落地的池推翻重来。**

## 二、"缓解经济压力"这条理由，实测上是绕路

真正的瓶颈今天量得很清楚：**岗位数恒为 10（jobs.json 6 + production.json 4），与 N 无关**
（克隆体只拿 `{id, persona, spawn, home}`，**从不进岗位表**，`Sim.gd:702`）。
于是 60 个人睡觉、而泥瓦匠永远只有一个。

多镇之所以"能缓解"，是因为**每个镇有自己的一套匠人 ⇒ 岗位数跟着镇数涨**。
**但那是"让岗位数随规模涨"的一个副作用，不是它本身。**
更直接的两条（都便宜得多）：让克隆体能就业；或给岗位加学徒位（评审在 §0.5 那轮就提过）。

⇒ **如果目标只是经济压力，多镇是最贵的解法。**
   ⇒ 所以立项理由应当是 §〇 那条社会性的，而经济互补作为**附带**收益。

## 三、它真正新增的东西（今天完全不存在的）

1. **有延迟的信息传播**：镇 A 的事，要**几天**才到镇 B，且**经由一个具体的人**。
   今天的谣言传播是同镇内即时的；跨镇 + 延迟 + 可追责的载体是**新机制**。
2. **地方性差异**：A 镇缺柴、B 镇缺瓦 ⇒ 价格/声誉/怨气**因地而异**，
   而今天全镇共用一本库存、一个缺货叙事。
3. **旅人这个社会角色**：他在两边都是"半个外人"——这是今天没有的社会位置。

## 四、若立项，先做哪一半（**建议：先做人，不先做货**）

**先做"人和消息能跨镇"**，把货运推到第二步。理由：

- 它直接检验 §〇 那条主诉（社会通道），而**不需要**先解决"跨镇贸易是微观还是宏观"（§一③）。
- 它对经济只有加法（多一个镇 = 多一套岗位），**不改动刚落地的池**。
- 它可以在**一个镇的数据结构**里先验证：给现有小镇加一个"外来旅人"来源，
  看谣言/声誉是否照预期扩散——**在造第二个镇之前就能证伪主诉**。

⚠️ **M2 刚发现的那件事对这里是硬约束**：
**social 是五个需求里唯一没有无条件满足者的**，而旅途中的 agent 天然远离社交池。
**"路上的人"极易掉进 M2 刚修好的那个吸收态。**（M2 实测：跌破门之后 3087 个 tick 候选恒为 0。）
⇒ **任何旅行设计都必须先回答"路上的人怎么维持社交"**，否则会直接复现刚修掉的 bug。

## 五、结论（我的判断，供用户决定）

**值得做，但不是现在这个形状。**

- **改写立项理由**：主诉是社会通道（有延迟、有载体的跨镇信息传播），经济互补是附带。
- **先补 §0.5 一行**：60 是"每镇"还是"全区域"。**这一行不写，后面所有验收都会重演今天的歧义。**
- **先做人与消息，后做货运**——货运牵扯"微观还是宏观"，而那是刚落地的池的判断，别急着重开。
- **先在单镇上证伪主诉**（外来旅人 → 谣言扩散是否如预期），再造第二个镇。
- **路上的社交**是先决条件，不是细节。

**下一步（本文提议、待用户点头）**：派一根**只读的可行性棒**，回答三件事：
① 跨镇需要新增哪些状态、它们各自会不会进 `Inv.digest` / `chain_step`；
② "外来旅人"能不能在**不改现有数据结构**的前提下先做出来（若能，主诉可以在一周内被证伪）；
③ 路上的 agent 的社交怎么维持——给出至少两种方案与各自的负对照设计。
