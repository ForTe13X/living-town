# World generation kernel slice

This checkout contains a reusable Godot add-on at `game/addons/worldgen`. Recipes are data-only, operators are typed and versioned, the executor records deterministic stage evidence, and packages separate semantic layout from presentation hints. Residents, save state, reservations, and game actions stay outside the immutable world package.

## Build the three current recipes

From the repository root with the pinned Godot 4.6.2 binary:

```powershell
$godot = '.\\build\\godot\\Godot_v4.6.2-stable_win64_console.exe'
& $godot --headless --path .\\game --script res://addons/worldgen/core/worldgen_build_cli.gd -- res://addons/worldgen/recipes/coastal_neighborhood.json res://addons/worldgen/builds/coastal_neighborhood.world.json
& $godot --headless --path .\\game --script res://addons/worldgen/core/worldgen_build_cli.gd -- res://addons/worldgen/recipes/inland_neighborhood.json res://addons/worldgen/builds/inland_neighborhood.world.json
& $godot --headless --path .\\game --script res://addons/worldgen/core/worldgen_build_cli.gd -- res://addons/worldgen/recipes/standalone_cafe.json res://addons/worldgen/builds/standalone_cafe.world.json
```

The coastal adapter packages the authored S1 topology and normalized integer-q access data. `worldgen.inland_layout/1` performs deterministic bounded parcel packing, emits rectangular building envelopes and an explicit connected road graph with driveway junctions. `worldgen.interior_program/1` creates a three-zone café, explicit access-controlled portals, capacity-bearing affordance slots, and declared route polylines. Both operators enforce operation budgets and reject impossible inputs. The inland operator also compiles each recipe building's explicit `rooms_required` and `affordances_required` into covered room partitions, access-controlled portals, and stable affordance/approach/route records; the current bounded layout uses deterministic vertical room strips rather than a general room solver.

Each result uses `WorldPackage/1`, separates semantic and presentation payloads, records recipe/stage hashes and operation counts, and is stored by content hash below `game/addons/worldgen/builds/objects/`. The named `.world.json` file is a convenient package copy. Strict JSON contracts are under `addons/worldgen/contracts/`.

## Export standalone Godot consumers

Run the exporter once per package. For example:

```powershell
python .\\tools\\export_worldgen_godot.py --package .\\game\\addons\\worldgen\\builds\\inland_neighborhood.world.json --output .\\out\\worldgen-viewer-inland
```

Use `coastal_neighborhood.world.json` or `standalone_cafe.world.json` and a distinct output directory for the other packages. The exporter verifies semantic and presentation digests, writes the package plus the read-only loader, and includes a code-only plan renderer backed by `WorldPackageSceneBuilder`. The builder instantiates editable native Godot nodes for road graphs, parcels, building footprints and collision polygons, room polygons, portal markers, and affordance/approach markers, carrying stable package IDs as node metadata. Pass `--blender-preview-dir` to include a digest-matched proxy GLB and make `proxy_3d_viewer.tscn` the main scene. The consumer copies no Living Town scripts or data, authoring executor, `.blend` source file, or model-service dependency. The plan view is semantic/debug geometry and is not production art.

Each exported project also contains `tests/offline_load.gd` and a pinned expectation fixture for the three current local packages. In a fresh code-only export, run `godot --headless --path <export-directory> --script res://tests/offline_load.gd`. The renderer-free gate checks whole-package and section digests, exact read-only query IDs, capability refusal, missing semantic topology, and malformed package roots. Run it once for each of the three packages and keep the receipts separate from Living Town gameplay evidence. The gate covers this repository's local `WorldPackage/1` profile; the LT-22 multifloor café/street snapshot and external v5 conformance remain separate qualifications.

An opt-in Sim activation example for the coastal package lives alongside the SpaceGraph overlay at `game/coastal/warm_bay_s1/export/sim_adapter/activation.example.json`. It is disabled. Live startup otherwise reads existing authored data unchanged. The coastal importer is read-only.

## Extension points

- `WorldGenOperatorRegistry` registers versioned pure implementations and declared ports.
- `WorldGenRecipeCompiler` checks references, port types, and cycles before execution.
- `WorldGenStageExecutor` runs a stable order and hashes typed output artifacts.
- `WorldGenArtifactStore` writes canonical JSON objects under their digest.
- `WorldGenPackageValidator` and `WorldGenPackageLoader` verify digest closure and package capabilities.
- `WorldPackageSpatialQueries` exposes detached read-only room, portal, affordance, building, and road queries to host-game adapters. Access filtering and deterministic near-affordance ordering operate on package definitions only; action legality, reservations, and state changes stay with the host simulation.

Recipes cannot carry executable expressions; operators are trusted project code. `canon.ascii_int32/1` rejects unsupported types and out-of-range numbers. Integral JSON values are normalized because Godot's parser may represent them as floats.

## Runtime spatial query facade

`core/world_package_spatial_queries.gd` is copied into every standalone Godot export. Configure it with a package returned by the validated package loader; it revalidates and keeps a private deep copy. Queries return detached dictionaries for rooms, portals, affordances, buildings, and roads. `query_affordances_near` uses package-local cell coordinates and orders ties by stable affordance ID. Named access profiles filter room, portal, and affordance definitions. The runtime validator now preloads its canonical hashing helper directly, so a fresh exported project does not depend on Godot editor global-class cache generation.

The facade reports static package affordances only. It does not make an affordance legally usable for a resident, infer social/economic effects, mutate the package, or reserve capacity. A host adapter must pass a returned definition through the existing game legal-action and commit path and retain authority over live occupancy and state. The standalone café runtime smoke produced 1 public room, 3 staff-visible rooms, 1 public portal, and 5 public / 6 staff affordances. This confirms package reads and profile filtering in an exported project, not actor movement or live game integration.

## AI-town spatial adapter

It retains package and room IDs, builds single-storey interior bounds and partition walls, maps exterior/internal portals, and prepares distinct home start cells. It resolves affordance actions only through `action_bindings.json` and copies an existing host advertisement, including its need and duration. Staff doors and work slots require an explicitly assigned host job title; package generation cannot grant that role. The inland layout operator places an interior doorway off the room-centre affordance row so the generated rest slot cannot block the only route into an adjacent room.

`WorldGenAitownAdapterCLI.gd` compiles the inland package, host graph/interiors/actions, and the first eight authored residents into `out/worldgen-aitown-adapter/`. The root `worldgen_activation.json` is disabled by default. Enabling it makes `Sim._load_data` merge the package before creating receiver-owned authority snapshots and applies the explicit eight-resident home assignments.

After the doorway placement fix, the package identity is `inland_neighborhood_s0 / 8403f6add04d0cbaaf29380d6bd01779225959dd6a7302e28c566eb6c6592524`; the shipped activation file is updated to that digest and remains disabled. The isolated walkthrough project at `out/worldgen-runtime-review/` enabled the package only in its copied project. This covers that scenario's entry/use/save-load path; engine player-trace replay and broader resident traversal remain unverified.

Package-backed schema-2 saves now carry receiver-authored `{world_id, semantic_sha256}` in the reserved `meta._world_package_ref`. Quickload checks that reference against the current opt-in package and still requires exact saved spaces, portals, and interior data. Older schema-2 saves without the reference can only backfill it when those embedded topology snapshots match exactly. Schema-1 saves are refused for package-backed worlds because they do not carry sufficient topology authority. Changed topology still fails closed during ordinary quickload. A separate reviewed offline migration now maps spaces/floors and coordinates, cancels active options, and rewrites topology snapshots into a new candidate; see the migration CLI section below. Portal and affordance actions are deliberately regenerated/cancelled rather than individually preserved.

For an approved structural change, enable the intended target package in `game/worldgen_activation.json` before invoking the CLI. `WorldSaveMigrationCLI.gd` writes a separate candidate save and never overwrites its input. Its `worldgen.aitown-migration/1` manifest binds exact `from` and `to` package references, maps every saved space and floor, supplies an integer `[dx, dy]` offset for every source plane, and must declare `active_action_policy: "cancel_all_agent_options"`. The transform rebuilds interior action objects from the target package and preserves resident records while updating spatial addresses. Current saves with a player replay trace are refused because the old trace boundary cannot be claimed valid after a topology change. The CLI runs the complete target Sim state and save-shape validators before writing. It is compile-validated but has not yet been exercised against real source/target migration fixtures.


## Authoring catalog and safe publication

`tools/worldgen_catalog.py` is an authoring-only SQLite catalog and immutable package store. It persists canonical package bytes at a SHA-256-derived path before attempting a SQLite `BEGIN IMMEDIATE` revision compare-and-swap. The catalog is the only active-build authority; failed or stale commits can leave unreferenced objects, while the prior head remains resolvable. Published history is retained; there is no garbage collector yet. Validation receipts use `contracts/worldgen_validation.schema.json`; reviewer receipts use `contracts/worldgen_approval.schema.json`. The publisher checks that both receipts bind to the candidate and expected base revision, but reviewer identity is an auditable claim, not a cryptographic signature. Current Godot-generated receipts for the three packages are under `out/worldgen-validation/`; no catalog publication has been made because no human approval receipt was supplied.

Example publication flow (the validation and approval JSON must come from the actual independent review process):

```powershell
python .\tools\worldgen_catalog.py --catalog-root .\out\worldgen-catalog publish `
  --candidate .\game\addons\worldgen\builds\coastal_neighborhood.world.json `
  --validation .\build\evidence\coastal-validation.json `
  --approval .\build\approvals\coastal-approval.json `
  --expected-revision 0
python .\tools\export_worldgen_godot.py --catalog-root .\out\worldgen-catalog `
  --world-id warm_bay_s1 --output .\out\worldgen-viewer-published
```

The exporter resolves a catalog snapshot read-only, writes a frozen package into the standalone Godot project, and records the build ID/revision in `export_manifest.json`. The consumer does not include SQLite, Python, Blender or the provider process. Existing direct `--package` exports remain available for development candidates that have not been published. The six Python catalog tests cover file durability, same-base CAS conflicts, receipt binding, duplicate JSON keys, corruption rejection, and catalog-to-project export. Godot package checks are separately recorded above; neither test layer establishes actor traversal, replay, or target-device behavior.

The authoring executor now has a persistent successful-stage cache (`core/build_cache.gd`) and reverse dependency index (`core/dependency_index.gd`). Cache identity contains recipe identity/revision, operator specification and source-code hashes, validator source/policy, every input-port digest, effective parameters, seed and budget policies, pins, boundary, candidate-set and structural/visual pack manifests. A missing source fingerprint disables cache reads/writes. Cache corruption is rejected and the stage is regenerated. Only successful stage outputs are stored; cancellation and failed stages are never cached. The focused `tests/worldgen_build_cache_test.gd` runner passes cold/warm reuse, palette-stage separation, door and allowed-candidate invalidation, corrupt-entry recovery, cancellation, and deterministic provenance checks. Cold and warm coastal builds also produced the same immutable build ID (`9fc12d10…`) while reporting zero and one cache hits respectively. Palette-only topology reuse is available when recipes separate topology and presentation into stages; current combined neighborhood operators remain coarse-grained. Cache reference retention/garbage collection and integration into the full recipe catalog remain outstanding.

WG37's edit kernel is in `core/edit_command.gd` and `core/diff_classifier.gd`. Patches are revision-bound and limited to named stage parameters with explicit visual/semantic field allowlists. Preparation deep-copies the source recipe, increments its revision, and captures protected object IDs. Candidate classification hashes the actual semantic and presentation sections, computes a conservative dependency closure, and refuses to treat semantic or mixed output changes as visual-only. `tests/worldgen_edit_command_test.gd` covers visual-only output, door relocation, stale bases, protected anchors, and a structural-output spoof against a visual patch.

WG38 has a first bounded repair kernel in `operators/local_repair.gd`. It consumes a finite allowed assignment set for declared dirty IDs, uses deterministic MRV ordering with each prior assignment tried first, freezes all other placements and boundary interfaces, honors hard pins and protected IDs, and reports the actual changed IDs/edit count and searched operation budget. A local failure reports `UNSAT_WITH_FIXED_BOUNDARY` and an explicit scope-expansion action; budget exhaustion is distinct and neither result claims global impossibility. A solved candidate is marked pending until an independent global validator returns evidence bound to its exact candidate digest. `tests/worldgen_local_repair_test.gd` covers locality, pin and boundary retention, old-placement preference, deterministic output, fixed-boundary unsat, budget exhaustion, hidden scope widening, and validation binding.
