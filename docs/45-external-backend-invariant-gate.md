## 一、门：`bench/BackendGate.gd`

```bash
godot --headless --path game res://bench/BackendGate.tscn -- --seeds 1-4 --days 8 --agents 12
```

两条 arm 夹住剂量的两端（中间的都被夹住）：

| arm | 是什么 | 为什么要它 |
|---|---|---|
| `random(full)` | `--decode-ticks 0`，L/C = 100% | **最严**的一档：每一次决策都由后端挑。这里守得住，任何更低剂量必然守得住；且零 `_wait`、最便宜 |
| `random@K=2` | 复刻真 SLM 的串行解码剂量（docs/38 §1.2 标定，与 slm 的 L/C 61-63% 配平） | 只跑 full 不够：`K>0` 才会走 `_pending` / `_wait` / 迟到回包重验那条**异步落地路**，代码路径不同 |

每条 arm × 每个 seed 断言三件事：

* **A** 所有【硬】不变量绿（含 #01；软/诊断只报告——8 天小网格本就不该硬断言涌现统计）
* **B** 同 seed **两跑**：`Inv.digest` / `Sim.event_digest` / 逐 tick 前缀链 **三路一致**
* **C** 饿穿 agent-tick ≤ `--max-starve`（默认 0 = #01 原口径）

### 1.1 为什么这条门可以进 CI，而 `slm` 永远不能

`random` 的选号来自项目自己的确定性种子流 `Sim._rng_at(RANDOM_SALT, who)`，**不是 `randi()`**，
且合成解码时延**按 tick 计**而非墙钟 ⇒ 同 `(seed, tick, agent)` → 同一选择，逐字节可重跑，
跑得快的机器不会拿到不同剂量（docs/38 §1.1 三跑同 digest，含 `--realtime` 开/关）。
**上面的断言 B 就是把这条性质机检了**——它不是注释里的承诺，是每次 CI 都重新证明一遍的事实。

`slm` 有 run-to-run 噪声（docs/38 §七-3），永远不进 CI。但两条臂走的是**同一条落地路**
（`decide` → 闭集选号 → `_cand_key` 重验 → `agent_apply`），所以这条路上的结构性护栏一旦立住，**两条臂同时受保护**。

> ⚠ 口径细节：本门的饿穿计数跟 `Harness._run_once`（不按 agent 去重，一个人同时饿又困计 2），
> 与 `BackendBench` 的 `starve_ticks`（per-agent-tick，带 `break`）**差一个 `break`**。
> 判定不受影响（同零同非零），但引用数字时别混。跟 Harness 是因为 #01 的口径由喂给 `Invariants.check_all`
> 的那个数定义，而那个数一直是 Harness 产的。

### 1.2 落地前的读数（未修的树上）

`--seeds 1-4 --days 8 --agents 12`，**8/8 红**，且 **#01 是唯一变红的硬不变量**：

| arm | seed 1 | seed 2 | seed 3 | seed 4 |
|---|---|---|---|---|
| `random(full)` | 659 | 838 | 699 | 1813 |
| `random@K=2` | 625 | 16 | 6 | 16 |

## 二、★ 根因：引擎的生存保护是【打分】，不是【禁令】

引擎有两层生存保护，而**两层都不约束外部选择**：

1. `_social_candidates`（`Sim.gd:1498`）在 `min_need < SURVIVAL_GATE(32)` 时返回 `[]`
   —— 这一层是真的**把社交候选摘出候选集**，对谁都有效；
2. `_logic_decide` 靠 urgency 主导的 `score` 让"吃/睡"胜出 —— 这一层**只是打分**。

第 ② 层对 `_logic_decide` 有效，对"在同一候选集里按下标挑一个"的外部后端**完全无效**：
晒太阳 / 看摊 / 做活照样在候选集里，模型或随机挑中它就照样落地。

**#01 是【硬】不变量**——按 `Invariants.gd:382-387` 的两分法，硬 = 结构性、任何 LOD/规模/激进降频下都必须为真。
它不该建立在"外部后端会自觉挑对"之上。engine makes opportunity, backend proposes ordering ⇒
**"能不能把人饿死"这件事必须由 engine 判，不能由 ordering 决定。**

## 三、修：两条边界，都只长在外部后端那条分支上

放在 `_advance_agent` 里 `backend.decide()` 的回值上，与既有的 **P2-2 合法边界** `_object_intent_ok`
（"可插拔 backend 可能塞来残缺字段 → 除零/索引失败"）是**同一族**：那条守**合法**，这两条守**活得下去**。

| | 判什么 | 口径 |
|---|---|---|
| **P2-3a `_survival_ok`** | 决策那一刻 | `min_need < survival_veto_line(=SURVIVAL_GATE 32)` ⇒ 只接受**正在救某条已告急 need** 的 intent |
| **P2-3b `_horizon_ok`** | 这趟差事付不付得起 | 成本 = 曼哈顿距离 + `dur_total`；预算 = `(min_need − line) / decay`。付不起 ⇒ 驳回 |

驳回 = 改走 `_logic_decide`（引擎地板），**不是**否定后端的排序权：**不在危机中时后端想挑什么挑什么**——
这是护栏便宜的原因（§4.2：出货剂量下只动 7.3%）。

**但危机中的实际语义要说准**（否则就是一句注释在骗人，见 §5.3）：`min_need` 一旦跌破线，
`_horizon_ok` 的预算变为负数 ⇒ **任何 object intent 一律驳回、引擎地板全面接管**。
`_survival_ok` 的分档（"带 need 且那条 need 已告急才放行"）此时只在 **非 object** intent
（social / attend）上承重；在 object 上被 `_horizon_ok` 吸收。**危机中不给自由度**是实测选出来的，不是设计洁癖。

### 3.1 ★ 零扰动：金标一个字节没动

两条边界的调用点都在 `if backend != null and backend.has_method("decide")` 分支内 ⇒
`backend == null`（金标 / Harness / DetGate 的红线#2 地板）时**永不被调用**。

实测：`bash tools/ci.sh` 全绿，S0 金标 12/12 可比、DetGate 16/16 可比，`golden_digests.json` 逐字节未动。
**本次改动没有、也不需要重烘任何金标。**

### 3.2 `_horizon_ok` 是被一条逐 tick 追踪逼出来的，不是先验设计

只上 `_survival_ok` 时，`random(full)` 的 seed 2 仍漏 **11** 个 need-tick。逐 tick 追下去，
漏的那一下**不是挑错了**——agent 正走在去灶台的路上：

```
tick=1506 hunger=36.3 pos=(21,30) | opt=object/看摊 need=fun rem=24 target=counter_1
...
tick=1636 hunger=0.0  pos=(41,16) | opt=object/吃饭 need=hunger rem=18 target=stove_1   ← 还在走
```

tick 1506 时 `min_need = 36.3 > 32`，`_survival_ok` 放行是**对的**——但那趟差事要
34 格路 + 24 tick 使用 ≈ **58 tick**，而 hunger 以 0.28/tick 掉，`(36.3−32)/0.28 ≈ 15 tick` 就跌破生存线。
**这张支票一开始就付不起。** 等承诺 pre-empt 在 `need<12` 抢回来时，已经走不到灶台了。

`_horizon_ok` 用的距离是 `_object_candidates:1489` 给 `score` 算距离惩罚的**同一个 `dist`**，
不新引入代价模型；`decay` 是 `needs.json` 里的常量，所以预算是**精确的 tick 数**。

## 五、★ 两条走不通的路（留作路标，别再走一遍）

### 5.1 把承诺 pre-empt 的抢占线提到 32 —— 炸了两个量级

看上去是最自然的补法（"既然长承诺付不起车费，那就早点抢回来"）。实测（只在外部后端驱动时提线）：

| arm | 抢占线 12（原） | 抢占线 32 |
|---|---|---|
| `random(full)` 4 seed 合计 | 11 | **13114** |
| `random@K=2` 4 seed 合计 | 0 | 397 |

**抢占线一提，`min_need<32` 期间任何不救急的 option 每 tick 都被打断 → 决策黏性没了 → livelock**：
人一直在"重决策—走两步—又被抢回"里空转，什么也办不成，于是饿穿。
`PREEMPT_CRISIS` 注释里那句"既有决策黏性(消 livelock)又不会饿穿"是**两个都承重**的约束，不是修辞。
**抢占是止损；真正该做的是一开始就别签这张支票**（= `_horizon_ok`）。

### 5.2 危机中"把先救哪条留给后端" —— 4 seed 看着绿，12 seed 漏

写完 §三 我注意到一处**看起来像疏漏**的地方：`min_need` 跌破线之后 `_horizon_ok` 的预算恒为负，
于是危机中任何 object intent 都被否——`_survival_ok` 那层"同时两条告急时先救哪条仍归后端"
**变成了死代码，而注释还在声称它活着**。自然的修法是把危机档的死线从生存线放宽到真饿穿线 `STARVE_NEED`。

改完 **4 seed × 8 天仍然 8/8 全绿**。**12 seed × 20 天漏了**（seed 3 @K=2：饿穿 15）。
宽出来的那点预算刚好够 agent 挑一条更远的救急路、然后没走到。

两条教训，第二条更重要：

1. **那不是疏漏，是承重结构。** 危机中就该不留自由度。已回退，并把这件事**写进代码注释**——
   宁可留一段"这里为什么故意不对称"的说明，也不留一个注释声称还活着的死档。
2. **CI 里那个 4 seed × 8 天的网格挡不住这个。** 它是**冒烟**，够用来抓"改坏了"，
   **不够用来给设计取舍拍板**。本文所有取舍都另跑了 12 seed × 20 天 + N=48 才敢下结论。
   （门本身保持在 4×8：CI 要快；宽网格是人工复核的事，命令见 §七。）

### 5.3 一个把我自己骗了一轮的度量 bug

第一次报"护栏吃掉 93% 的模型决策"——**是错的**。`ext_veto` 忘了在 `start_new` 里清零，
跨 seed / 跨扫描档累加，于是"有效 L/C"一路算成负数。修好后是 7.3%。
教训与 docs/36 §复现 那条同源：**任何跨 seed 复用的计数器，先问它在哪儿清零**
（`AIBackend.reset_stats` 早就为此存在，新加的探针漏进了同一个坑）。

顺带一个真结论：`ext_veto` 必须**只计真的换掉了的**。`backend.decide()` 在 worker 忙 / 节流 /
预算门 / 过载这些档位下返回的本来就是 `_logic_decide` 的结果，那些也会走到否决分支，
而重算一次是同一个纯函数同一份输入 → **逐字节同一个 intent，什么也没改变**。
把它们也计进来，"引擎驳回了后端多少次"会虚高一个量级（K=2 档：1483 vs 真实 117）。

## 七、复现

```bash
# 门（CI 步骤 4d 跑的就是这条）
godot --headless --path game res://bench/BackendGate.tscn -- --seeds 1-4 --days 8 --agents 12

# 更宽的网格 / 更大的镇子
godot --headless --path game res://bench/BackendGate.tscn -- --seeds 1-12 --days 20 --agents 12
godot --headless --path game res://bench/BackendGate.tscn -- --seeds 1-4  --days 8  --agents 48

# 看护栏的代价（"其中被【生存否决】换掉 N 次 → 有效决策占比"那一行）
godot --headless --path game res://bench/BackendBench.tscn -- --backend random --agents 12 --seeds 1-4 --days 8 --decode-ticks 2

# 证明金标没动
GODOT=<godot> bash tools/ci.sh          # S0 金标 12/12 可比 + DetGate 16/16 可比 全绿
```

否决线是 `Sim.survival_veto_line`（默认 `SURVIVAL_GATE`），改它即可复现 §4.3 的扫描。
