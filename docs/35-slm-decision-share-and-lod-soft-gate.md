## 一、SLM 决策占比：landed/fired ≠ 决策占比

### 1.1 为什么 landed/fired 不能当占比

`landed/fired` = 「**我们选择发出去的**请求里，有多少按时回来」。
`landed/decisions` = 「全镇落地的决策里，有多少是模型做的」。
两者之差 = **因为串行 worker 正忙、根本没发出去的那一大片决策**——它们是真决策（由引擎地板做的），
却既不进分子也不进分母，于是在 landed/fired 里完全隐形。

分母怎么数（对照 `Sim.gd` 的 backend 路径 `intent = backend.decide(...)`）：

| `decide()` 返回 | Sim 的动作 | 算一次决策吗 |
|---|---|---|
| 非空 intent | `agent_apply(ag, intent)` | ✅ 模型决策 |
| `{}`（空） | `_logic_decide` 兜底后 `agent_apply` | ✅ 引擎决策 |
| `{"_wait": true}` | `return`，下 tick 拿同一 agent 再问 | ❌ **必须剔除** |

⇒ `decisions = calls − waits`。等待期的重复轮询必须剔掉，否则不但虚增分母，
**虚增幅度还与推理延迟正相关**（模型越慢轮询越多）——留着会让慢模型看起来更"忙"。
实现在 `AIBackend.decision_stats()`（`stats.calls` / `stats.waits` 两个纯计数器；
CI 恒 `Sim.backend=null`，`decide` 根本不被调用 ⇒ 对 digest 零扰动，已逐字节验证）。

### 1.2 串行 worker 的墙钟天花板（与 N 无关）

`_slm_submit` 一次只放一发（`_slm_busy`）。1 sim-日 = `TICKS_PER_DAY(240) × tick_interval(0.08s)` = **19.2 s 实时**
（`Sim._process` 是累加器：掉帧只会在一帧里多补几个 tick，不会把 sim-日拉长）。
⇒ 单发解码 D 秒 ⇒ **全镇上限 = 19.2/D 次每 sim-日，与镇上有多少人无关**。
分母却随 N 线性涨 ⇒ **N 越大，真实占比越低**。

| 解码 D | 全镇上限（次/sim-日） |
|---|---|
| 0.22 s（本机 GPU 饱和实测） | ~87 |
| 3 s（8Elite CPU 暖发下限，docs/34） | 6.4 |
| 8 s（暖发上限，docs/34） | 2.4 |

### 1.3 分母实测（确定性，backend=logic，可精确复现）

```
godot --headless --path game res://bench/BackendBench.tscn -- --backend logic --seeds 1-3 --days 20
godot --headless --path game res://bench/BackendBench.tscn -- --backend logic --seeds 1-2 --days 20 --agents 60
```

| cast N | 落地决策 | 折合 |
|---|---|---|
| **12**（出货默认，`agents.json` 就是 12 人） | 5234 / 60 sim-日 | **87.2 次/sim-日** |
| **60**（上限 cast） | 21377 / 40 sim-日 | **534.4 次/sim-日** |

（`waits=0`，因为 logic 后端从不返回 `_wait`。这两个数是确定性的，同 seed 逐次可复现。）

### 1.4 端到端实测（真模型，**按出货节奏**）

新增 `--realtime`：按 `Sim.tick_interval` 的墙钟推进 tick（复刻 `_process` 累加器：落后就连补、不补睡）。
**没有这个开关，占比不可外推**——默认 bench 是 0.03s/tick，1 sim-日只花 7.2 s，等于白送模型 2.7 倍的思考时间。

```
godot --headless --path game res://bench/BackendBench.tscn -- --backend slm --seeds 1 --days 4 \
      --agents 12 --realtime --model <绝对路径>/qwen2.5-1.5b-instruct-q4_k_m.gguf
# 加 --cpu 走 CPU 解码；--agents 60 换 cast
```

模型 = Qwen2.5-1.5B-Instruct Q4_K_M，seed 1，4 sim-日，三跑均实测「1 sim-日 ≈ 19.2 s」（节奏相符）：

| 配置 | fired | landed | **landed/fired** | 落地决策 | **landed/decisions** | 模型决策/sim-日 |
|---|---|---|---|---|---|---|
| N=12, GPU | 205 | 165 | 80.5% | 323 | **51.1%** | 41.3 |
| N=12, CPU | 124 | 91 | 73.4% | 305 | **29.8%** | 22.8 |
| N=60, GPU | 351 | 273 | 77.8% | 1858 | **14.7%** | 68.3 |

**这张表就是全部论据**：`landed/fired` 三跑挤在 **73–81%** 的窄带里纹丝不动，
而真实占比从 **51% 一路掉到 15%**。也就是说，决定占比的两个变量（cast 大小、解码快慢）
`landed/fired` **一个都感知不到**。拿它当占比，等于拿一个与答案无关的量去回答问题。

（附注：N=60 时模型决策/sim-日反而**升**到 68.3——N=12 时串行 worker 有空转，N=60 请求排满才逼近饱和。
天花板是真的，只是 N=12 没跑满。）

### 1.5 真机占比（用 docs/34 的既有真机数据 + 上面的确定性分母）

docs/34 记录的 CPU 端到端眼验：`发起 51 · 成功 34`，**跑到第 19 sim-日**。

- 模型决策 = 34 / 19 ≈ **1.79 次/sim-日**
- 发起 = 51 / 19 ≈ **2.68 次/sim-日** → 落在 §1.2 天花板区间 [2.4, 6.4] 内 ✅（解析式与实测互证）
- 分母（cast=12）= **87.2 次/sim-日**
- ⇒ **真实占比 ≈ 1.79 / 87.2 ≈ 2%**

**结论（限定版，勿再外推）：在【那台手机 · 那次运行 · N=12 · 该解码速度/热状态】下，端侧 SLM 落地的决策约占全镇 2%，而不是 2/3。**

⚠️ **不要把这个 2% 说成"端侧 SLM 只做 2% 的决策"**（2026-07-26 外部对抗评审 GPT-5 Pro 指出，已采纳）：
- **桌面本机推理也是"端侧"**，同一诚实口径下是 **14.7%–51.1%**（§1.4）。把 2% 当作端侧模型的普遍占比，等于用一个过度外推替换掉另一个过度外推（67%）——正是本文要纠正的毛病。占比是 `(19.2/D) ÷ 每 sim-日决策数(N)` 的函数，**随解码速度与阵容规模变化两个数量级**，不存在单一常数。
- **`19.2/D` 是稳态吞吐近似，不是硬天花板**：D 是均值而非固定服务时间；跨日边界可能带入一次未完成的解码；真机满载时 tick 循环本身会被拖慢（sim-日的真实墙钟 > 19.2s），故"与 N 无关"只在**验证过实时节奏**时成立（`--realtime` 就是为此加的，桌面已验、真机未验）。
- **`calls − waits` 仍可能虚高分母**：若某些 tick 是"延续既有行动 / 只有唯一候选 / 被迫动作"，把它们都算成一次"镇级决策"会让占比偏小。诚实做法是**在 commit 边界计数**（唯一决策情节），而非在函数调用边界。
- **`landed` ≠ `drove`**：模型落地的编号可能与 logic 会选的**恰好相同**。故 `landed/decisions` 只是**影响力上界**；真正的干预率应做 **shadow 对照**——每次模型落地时，用同一份冻结候选集同时算出 logic 基线编号，统计二者**不同**的比例（Δ/C）。这个数尚未测，是下一步。

**这个 2% 的已知局限（不掩盖）：**
- 19 sim-日是从 docs/34 的叙述读出来的，不是埋点直出。若冷启阶段有若干日没产出，则稳态占比高于 2%。
- 分母 87.2 用 backend=logic 测得；SLM 在跑时全镇决策率略低（实测 76.3–80.8/sim-日，因为 `_wait` 期 agent 空转）。
  用 76.3 重算得 **2.3%**，量级不变。故本文只说「约 2%」，不写更精确的位数。
- docs/34 最后那次「合并版装机眼验」`发起22·成功13·超时0` **没记 sim-日数**，
  **算不出**占比，这里**不补猜测值**。要补就重跑并记下 sim-日数。
- N=60 的真机占比**从未测过**（每个真机数据点要么 N≈12+SLM、要么 N=200+logic）。
  按 §1.2/§1.3 外推为 **0.3–0.8%**，但这是外推，不是实测。

### 1.6 这改变什么决策

- **不改变**延迟工程的评价：池化 worker、端上默认 CPU、deadline 15s 都是真收益，
  `67% 的已发出调用落在线内` 仍是它们的正当指标。被推翻的只是从它跨到「决策占比」的那一步。
- **改变**"端侧 SLM 值不值它的 FPS 代价"的算法：真机上 CPU 推理让 FPS 88→34（docs/34），
  换来的是 **~2%** 的决策由模型做——而不是 2/3。这个交换比必须用真数字来谈。
- **提示了杠杆在哪**：占比的天花板是 `19.2/D`，所以**唯一能大幅提占比的是把 D 压下去**
  （更小/更规整的学生模型），而不是继续调 deadline 或并发——worker 是串行的，调并发也没有并发。

### 1.7 发声公平（L5）实测

`--agents 60 --realtime`，`llm_budget=0`（默认不限，故老化门**不生效**，是先到先得）：

| cast | 发声 Gini | 从未发声 |
|---|---|---|
| 12（GPU / CPU） | 0.139 / 0.121 | **0 / 0** |
| 60（GPU） | 0.308 | **1 / 60** |

（若将来 cast 再涨或改用预算制，这三行数字就是重测基线。）

## 二、LOD：用软不变量重新评审「激进 LOD 能不能默认开」

### 2.1 原有契约的适用边界

`LodAblation.gd` 的激进门写作 `agg_ok := cost_cut and no_mass_starve and live and agg.fh == 0`，
注释明写「软不变量按设计可漂」。**作为 bench 量成本的契约，这没问题**——远端 agent 变背景群演，
状态当然仍合法。**但它不是"要不要默认开"的证据**：软不变量量的就是涌现社交行为，
而涌现社交行为就是这个产品。用只查硬不变量的门去批准一个默认值，
等于用「状态没坏」证明「东西还好玩」。

### 2.2 新增：软不变量臂（**默认只报告，不成门**）

打印每个配置的软失败数、**失败的具体 id**、其中属诊断项（`Invariants.DIAG_IDS`，当前 = `[15]`）的数量，
以及接受度 Gini。失败条数**不写死**、诊断项**从 Invariants 读**——B1 刚把 #15 降级为诊断，
写死等于埋定时炸弹。`--soft-gate` 才把它变成门（要求激进版的非诊断软失败 ≤ off 基线）；
默认关，既有门的判定逐字节不变。

```
godot --headless --path game --script res://bench/LodAblation.gd -- --seeds 1-3 --agents 60 --days 20
godot --headless --path game --script res://bench/LodAblation.gd -- --seeds 4-6 --agents 60 --days 20
```

### 2.3 结果：两组独立 seed，**失败 id 完全一致**

N=60 × 20 天，每组 3 个 seed：

| 配置 | 软失败（seed 集 A: 1-3） | 软失败（seed 集 B: 4-6） | 失败 id（两组相同） | Gini A / B |
|---|---|---|---|---|
| off | 1 | 2 | `#8` | 0.101 / 0.103 |
| 保守 | 1 | 2 | `#8` | 0.105 / 0.096 |
| **激进** | **14** | **14** | `#8×3 #11×3 #14×2 #17×3 #26×3` | **0.033 / 0.031** |

**诊断项（#15）在所有 9 个格子里都是 0 次**——即这些红**全部**是真软不变量，
不是 docs/31 已判定为时间泄漏伪影的那一项。

被打掉的是什么（`Invariants.gd` 的原名）：

| id | 名称 | 断言 |
|---|---|---|
| #8 | 承诺生命周期 | 承诺被创建**且**被兑现 |
| #11 | 冲突生命周期 | 冲突被创建**且**被修复/对质 |
| #14 | standing 分化 | 全镇声望跨度 > 0 |
| #17 | 坏名声形成可恢复 | 出现负向事件**且**有修复 |
| #26 | 同派系亲和 > 跨派系 | 派系是真的 |

**#14 失败的含义要说白：全镇 standing 跨度塌成 0——所有人声望一模一样。**
这与 Gini 从 ~0.10 塌到 ~0.03（**−67% / −70%**）是同一件事的两种说法：
**激进 LOD 下小镇变成一群没有差别的人。** 承诺、冲突、名声、派系——五条全断。

**复现了先前的一次性观察**（off 1-2 条、激进 14 条、Gini ~0.10→~0.03），且两组独立 seed 的失败 id 逐条相同。

> ⚠ **本表的数字在 HEAD `53cb835` 上已经不成立了**（B10 重测，2026-07-26）。
> `7227517 fix(sim): 唤醒社交沉睡的一半` 之后 off 基线自己变好了，于是 seed 1–3 实测为：
> **off 3 条（`#8×3`）、保守 2 条、激进 13 条（`#8×3 #11×3 #14×1 #17×3 #26×3`）**，Gini `off 0.095 / 保守 0.109 / 激进 0.035`。

### 2.4 结论（2026-07-26 经 B10 判别实验**修订**；原文见下方引用）

> **原结论**（保留以便对照）：「激进（聚合）LOD 不应默认开……**#14 失败的含义要说白：全镇 standing 跨度塌成 0
> ——所有人声望一模一样。**这与 Gini 从 ~0.10 塌到 ~0.03（−67%/−70%）是同一件事的两种说法：
> **激进 LOD 下小镇变成一群没有差别的人。**承诺、冲突、名声、派系——五条全断。」

**B10 的判别实验（§2.6）把这段话的【方向】留下了，把【论据结构】推翻了。** 逐条：

| 原表述 | B10 之后 |
|---|---|
| 激进 LOD 不应默认开 | ✅ **仍成立**，且证据比原来**更强**（等交互量对照，§2.6.6）。唯一该加的限定：已知的是「**当前实现**必然如此」，根因未隔离 |
| 「Gini 塌陷可能只是观测假象」（评审提出的未排除解释） | ✅ **已排除，且方向相反**：把全保真按激进档的暴露/节奏降采样，Gini **升** +0.05~+0.13，不是降（§2.6.2） |
| 「standing 跨度塌成 0，所有人声望一模一样」 | ⚠️ **一半对**：跨度确实**字面为 0**（seed 2/4/6：3540 条关系的 standing 全部恰为 0.00；seed 1/3/5：跨度 1.0、非零仅 9~30/3540；方差 0~0.008 vs off 0.43~0.57）。但**成因不是「分化被抹平」，是「分化机制从没跑过」**——写 standing 的唯一路径 `_judge_actor` 只在**被拒**时触发，而激进档几乎无人被拒 |
| 「Gini 塌 67% ⇒ 小镇变成一群没有差别的人」 | ❌ **推翻**：这是 **Gini 的天花板效应**。激进档均接受率 **0.96**（off 0.42），60 人里 **42~50 人接受率恰为 1.000**。Gini 对「全体挤在同一个值」恒 ≈0——这与「社会分化被抹平」不是同一件事 |
| 「五条全断 = 五份独立证据」 | ❌ **推翻**：是**一个缺陷的五个症状**，一条因果链（§2.6.4） |
| 「代价是产品本身」 | ✅ **反而被加强了**：等交互量对照（§2.6.6）下 standing 三个 seed **全部恰好为 0.00**——不是「变慢」，是**没发生** |

- **修订后的结论（这是现在该引用的版本）**：
  **激进（聚合）LOD 不应默认开。** 它省 66% 候选枚举成本（**代理量，非设备实测**），
  代价是一条可复现的因果链：几乎无人被拒（接受率 0.42 → 0.96）⇒ 无 `_judge_actor` 负向评判
  ⇒ standing 恒 0 ⇒ 无怨气/无冲突/无修复/派系不分离，接受率全顶到 1.0。
  **且这不是速率损失**：把激进臂跑到与 off **相同的社交提议总数**（3.4× 时长）后，
  standing 方差仍是 **0.0000**、接受率**更高**（0.974）——结构性损失，不是「只是慢了」。
- **但要点名两处原来的证据错误**（结论对，理由错，下次不许再这么写）：
  1. **「Gini 塌 67%」不是独立证据，是天花板效应**——真正该报的量是 **standing 方差 0.49 → 0.0000**，不是 Gini 的百分比。
  2. **根因尚未隔离**。本轮提出并**亲手证伪**了两个根因假设（`_far_maintain` 的补给常数 §2.6.5、交互量不足 §2.6.6）。
     在根因定下来之前，**不要**说「聚合这件事本身必然如此」——已知的只是**当前实现**必然如此。
- **保守 LOD：软不变量层面仍无异议，但新打的原始量露出一条以前看不见的线**（N=60 seeds 1-3）：

  | | off | 保守 | 激进 |
  |---|---|---|---|
  | 接受度 Gini | 0.0950 | **0.1091（↑）** | 0.0352 |
  | 提议数/agent | 58.2 | **49.3（−15%）** | 17.1 |

  **保守门量的 `\|ΔGini\|≤0.05` 在这里指错了方向**：Gini 不但没掉还**升**了 0.014（远在门内），

  拿 Gini 当社会分化的代理量。⚠ **这只是 3 个 seed 的一次观察，没有逐 seed 分布，

  **不足以推翻「保守档无异议」，只够立一个待查项**：先用逐 seed 的 standing 方差重测，再谈要不要动那个门。

### 2.5 外部对抗评审（2026-07-26，GPT-5 Pro）提出的下一步——必须先做的判别实验

评审对本节结论最有价值的一击**不是**推翻它，而是指出**尚未排除的另一种解释**：

- **Gini 塌陷可能是"观测的"而非"行为的"。** 聚合档改变的不只是行为，还有**观测口径**——若聚合路径把一队人的结果池化、或对一整个 cohort 用同一个估计概率、或只上报其中一部分 agent，那么"接受率的 Gini"会**机械地**塌下去，而底层社交倾向其实没被抹平。

  - 若降采样后的全保真 Gini **也**塌 → 大部分是观测假象，§2.4 的力度要下调。
  - 若只有聚合仿真塌 → 是真行为差异，结论坐实。
- **"14 处失败跨 6 条不变量"很可能是相关症状而非 14 个独立证据**：单一缺陷（例如把一次聚合 standing 更新广播给每个个体）足以同时触发 #14/#26/#17/#11 与接受率分布变化。应报**逐 seed 效应量 + 首次因果分歧点**，而不是阈值越界计数。

- **默认值决策还缺性能侧**：LOD 存在的理由是性能。只有保真度数据不足以定默认档，需要真机上的 ms/tick、掉帧、热、功耗、可支撑 cast 上限，与保真损失并排看。

**故本节结论的当前强度应表述为**：*激进 LOD 在 N=60、该时长下可复现地改变社交分布指标并打破多条软保真不变量；保守档无此回归。在隔离出责任组件、并与其性能收益并排评估之前，激进档不应作为默认。* —— 这比"聚合 LOD 不应默认开"弱，也更准确（**保守档本就无异议**）。

#### 2.6.1 先把「聚合档到底改了什么观测」说清楚（这是判别实验的前提）

`lod_aggregate` 在 `Sim.gd` 里**只有 5 个触点**（`grep lod_aggregate` 全集）：

| 位置 | 做什么 |
|---|---|
| `tick()` | 每 tick 算一次满帧 cohort＝玩家 ∪ salient（`talking>0` ∨ `option≠null` ∨ `min_need<32` ∨ 玩家近旁）∪ 轮转（`\|hash(id)\| % 31 == tick % 31`） |
| `_advance_agent()` | far agent：`option=null` → `_far_maintain()` → **return**。不枚举候选、不决策、不提交社交 ⇒ **该 tick 完全不产事件** |
| `_advance_agent()` | LOD 专属生存网（`need<8 → +6`） |
| `_nightly()` | far agent 跳过 `_reflect_agent`（只写记忆，不入 digest/不变量） |
| `_nightly_active_ids()` | 结盟/派系聚类只在 cohort 内做 |

对照评审列的四种机械压低 Gini 的机制：

| 评审设想的机制 | 代码里是否成立 |
|---|---|
| 把一队人的结果**池化** | ❌ **不成立**。`event_log` 每条仍是「一个 actor / 一个 target / 一次 `_acceptance_rule`」；`_far_maintain` 只写 needs，一条事件都不产 |
| 对一整个 cohort 用**同一个估计概率** | ❌ **不成立**。聚合路径里根本不存在任何 group 级概率 |
| **只上报一部分 agent** | ⚠️ 机制存在（far agent 不产事件；`Metrics.gini_acceptance` 把 `prop==0` 的 agent **整个剔除**），但**实测从未触发**：N=60×20 天下 off / 激进**两臂的零观测 agent 数都是 0**（轮转保证每 id 每 31 tick 必有一满帧） |
| **减少每个 agent 的接受机会数** | ✅ **成立，且是唯一真实的观测变化**：提议数/agent **57.6 → 17.1（3.4×）** |

⇒ 判别实验只需针对最后一条。

#### 2.6.2 决定性对照：把全保真按聚合档的暴露/节奏降采样

三种降采样口径（均为 N=60、20 天、seed 1–6）：

- **D1 计数匹配**：每个 agent 只保留 `m_i` 条提议（`m_i` = 该 agent 在激进档的实测提议数，按其自身序列**均匀**抽）。
- **D2 提交期节奏**：只保留「事件发生那 tick，actor 在影子 cohort 内」的提议。
- **D3 决策期节奏**：只保留「该 option 被**创建**那 tick，actor 在影子 cohort 内」的提议——**最忠实**，因为聚合档的闸门在**决策**不在**提交**（有 option 的 agent 恒 salient、恒在 cohort 内）。

| 口径 | Gini 均值 | 逐 seed 极差 | 相对 off |
|---|---|---|---|
| off 全量 | **0.0970** | [0.0889, 0.1111] | — |
| **D1 计数匹配** | **0.1477** | [0.1290, 0.1620] | **+0.0507** |
| **D2 提交期节奏** | 0.0970 | [0.0889, 0.1111] | ±0.0000（**一条都没被滤掉**） |
| **D3 决策期节奏** | **0.2263** | [0.2047, 0.2439] | **+0.1293** |
| 激进仿真 | **0.0344** | [0.0267, 0.0381] | **−0.0626** |

**结论：观测假象假设被排除，而且方向相反。** 把全保真降采样到聚合档的暴露/节奏，Gini **升**（小样本噪声抬高离散度），
不是降。**「更少观测会机械地压低 Gini」在这个度量上根本不成立。**
（D2 恰好一条不滤，本身也是个有用的事实：提交期从来不是闸门。）

#### 2.6.3 但「Gini 塌 = 小镇变成一群没有差别的人」是**错的**——那是天花板效应

| 配置 | 均接受率 | 被拒条数/局 | 接受率恰为 1.000 的 agent |
|---|---|---|---|
| off | **0.424** | 1977–2066 | **0 / 60** |
| 激进 | **0.963** | 34–51 | **42–50 / 60** |

Gini 对「全体挤在同一个值」恒 ≈0。激进档 60 人里 42–50 人接受率**恰好是 1.000**，
所以 Gini→0 是**度量的天花板压缩**，不是「社会分化被抹平」的独立证据。
（零观测 agent 的处理口径在这里也不影响：改成按率=0 计入而非剔除，off 0.0970 / 激进 0.0344，**基本不动**。）

#### 2.6.4 「14 条红」是**一个因果链的五个症状**，不是 14 份独立证据

写 standing 的**唯一**路径是 `_judge_actor`，而它在通用社交里**只在被拒时**触发（`_commit_social` 的 `if not accepted` 分支）。于是：

```
聚合档几乎无人被拒 (0.963)
  → 无 _judge_actor 负向评判  → standing 恒 0        → #14 红
  → 无 _bump_resentment       → 冲突几乎不触发        → #11 红（触发 188 → 0~3）
  → 无冲突 ⇒ 无修复                                  → #17 红（修复 23~35 → 0）
  → 无差异化 affinity          → 派系不分离            → #26 红（off 同派系 0.3~4.0 vs 跨派系 −3.0~−3.4；激进两者都 ~+1）
  → 接受率全顶到 1.0                                  → Gini 塌（§2.6.3）
```

**#8（承诺生命周期）不属于这条链**：它在 **off 基线自己**就红（6 个 seed 里 5 个 `创建=0`），是 N=60 的基线事实，与 LOD 无关（§2.4 早已记录）。

**逐 seed 效应量**（原文只给了「越界计数」）：

| 指标 | off（seed 1–6 区间） | 激进（seed 1–6 区间） |
|---|---|---|
| 冲突触发 / 对质 / 修复 | 164–197 / 29–38 / 23–35 | **0–3 / 0 / 0** |
| L3 负向声誉事件 | 19917–21877 | 394–726 |
| standing 非零条数（共 3540 条关系） | 860–1065 | **0–30** |
| standing 方差 | 0.425–0.573 | **0.0000–0.0084** |

**#14「跨度塌成 0」是否字面为真：是的，一半 seed 上字面为 0。**
seed 2/4/6：3540 条关系的 standing **全部恰为 0.00**，跨度 0.00。
seed 1/3/5：跨度 1.00（−1..0），非零仅 9–30/3540，方差比 off 低 **50–200 倍**。
⚠ 但要注意 **#14 这条不变量本身几乎测不出东西**：它断言的是 `跨度 > 0.0`，
于是 seed 1/3/5 在方差低 200 倍的情况下**照样 PASS**。它的红/绿比它测的量noisy得多——
**该看原始跨度/方差，不该看它的 pass/fail**（`LodAblation.gd` 本轮已加打原始量）。

#### 2.6.5 被自己的反事实**推翻**的一个根因假设（留档）

从代码读出的假设是：`_far_maintain` 对任何 `<50` 的需求每 tick 无条件 `+AGG_RELIEF(6.0)`，
把 far agent 的 social 钉在 ~50；而 greet/invite 接受式的主项是 `(100−target.social)*0.4`（阈值 0，jitter ±10）
⇒ 主项恒 ≈20 ⇒ 几乎必接受。**看起来一行代码解释一切。**

**做了反事实臂就塌了**（探针 `agg+fix`：每 tick 把 far agent 的 social 钉到 off 实测稳态值而非 ~50）：

| 配置 | 时均 social | 主项 | Gini | 均接受率 | standing 方差 |
|---|---|---|---|---|---|
| off | 77.5 | 9.0 | 0.0970 | 0.424 | 0.4923 |
| 激进 | 60.5 | 15.8 | 0.0344 | 0.963 | 0.0027 |
| **激进+fix** | （钉到 77.5） | 9.0 | **0.0360** | **0.960** | **0.0002** |

**主项差其实只有 6.8 分（9.0 vs 15.8），不是我推的 2 vs 20**——因为 far agent 会轮转成 near 并真去社交，
两个池子是混的。把这 6.8 分抹平后**接受率纹丝不动（0.963 → 0.960）、standing 方差反而更低（0.0027 → 0.0002）**。
⇒ **`_far_maintain` 的补给常数不是根因，假设作废。**

⚠ **该臂本身有严重混淆，不要拿它的 Gini 说事**：改 social 同时改了「愿不愿**发起**」和「愿不愿**接受**」两侧，
把提议总数从 3675 打到 **264**（14×）。小样本会把 Gini 抬高（§2.6.2 的 D1/D3 已证），
所以「agg+fix 的 Gini 0.0714 比 agg 的 0.0229 更接近 off」**恰好是该被怀疑的方向**。
它唯一站得住的读数是：**standing 方差仍然是 0.0000——分化一点都没回来。**

#### 2.6.6 等交互量对照：不是「放慢」，是**真的没发生**

`--agg-days 68`：把激进臂跑到与 off@20 天**相同的社交提议总数**（激进档每 tick 的提议约为 off 的 1/3.4）。
若聚合档只是把涌现社交**放慢**到与它省下的成本同一个倍率，那么在等交互量下应当**追回来**。

| 配置 | 提议总数 | 均接受率 | 被拒条数 | standing 非零/3540 | standing 跨度 | standing 方差 | Gini |
|---|---|---|---|---|---|---|---|

⇒ **「聚合档只是把涌现社交放慢了」这一解释也被排除。** 这是结构性损失，不是速率损失。

#### 2.6.7 仍然未定的一件事 + 仍然欠的一件事

- **未定：为什么激进档几乎无人被拒？** 因果链的**近端**已经坐实（无被拒 ⇒ 无负向评判 ⇒ 无 standing 分化 ⇒ #14/#11/#17/#26 + Gini），

  ①「`_far_maintain` 把 social 钉低」→ §2.6.5 证伪；②「交互量不够、螺旋没点着」→ §2.6.6 证伪。

## 四、新增 `bench/slm_lifecycle_soak` — 池化 worker 的生命周期回归跑（**桌面夜跑，不进 CI**）

**为什么需要**：docs/34 记着这类 bug 翻过两次车——第一版"根因"(Adreno) 被自己的后续测试证伪，
第一版"修复"(C1) **反而重新引入了它要消灭的 use-after-free**，两次都靠对抗评审才逮到。
而自动化里**没有任何东西**覆盖这条路：`tools/ci.sh` 从不跑 `BackendBench` 或任何 SLM 测试，

`finish` 里显式断**两条**信号、换模型/换 GPU 的延后拆——**全无回归网**。

断言（每条都对应一个真出过的 bug）：

| | 断言 | 对应事故 |
|---|---|---|
| A | 进程活着退出 | 旧 per-call churn 版在此段错误 EXIT 139 |
| B | 存活 `NobodyWhoChat`/`NobodyWhoModel` ≤ 2 | 池化被破坏 → 回到 churn |
| C | `response_finished` 连接数 ≤ 2，且**空闲时必须归 0** | C2：`CONNECT_ONE_SHOT` 死闭包 O(submits) 累积 |
| D | 跑动中周期 `set_model_path` / `set_slm_use_gpu` / `cancel_all`（**故意撞在飞**） | C1：换模型同步 free 在飞 chat → UAF |
| E | `fired > 0` | 防"什么都没发生"式假绿 |

**运行方式是【场景】不是 `--script`**（实测：`--script` 模式下 Godot **完全不注册 autoload**，
`AIBackend.gd` 里对全局 `Sim` 的引用在**编译期**就报 `Identifier not found: Sim`，整个脚本加载失败。


### 4.1 它第一跑就抓到一个东西：**SLM 路径在【进程退出时】间歇性段错误（EXIT 139）**

⚠ **本节自己就示范了一次本文批判的错误，故把过程留在这里。**
第一次观察是：不扰动的一跑 EXIT 0、做过一次 `set_slm_use_gpu` 的一跑 EXIT 139
——我当场差点写下「只要拆建过模型，退出必段错误」。那是**每臂 n=1** 的因果结论。
重跑之后它站不住：

| 臂 | 跑法 | 崩 / 总 | 崩率 |
|---|---|---|---|
| 拆建过模型 | `--seconds 18~40 --swap-every 12~15`（1~3 次扰动） | **4 / 8** | 50% |
| 未拆建（对照） | `--swap-every 9999`（零扰动） | **1 / 7** | 14% |

50% vs 14%（n=8/7）**不足以判定因果**（Fisher 精确检验 p≈0.28）。**suggestive，未证实。**

**能站住的结论只有这些：**
1. 桌面 SLM 路径**会**在进程退出时段错误，**间歇性**，本轮 15 跑里 5 次（约 1/3）。
2. 它发生在**所有输出打完之后**、且**运行中断言全绿之后**——196 发 0 崩、池化 chat 恒 1、
   信号连接空闲期恒 0、C1 延后拆按设计工作。崩的是**进程 teardown**。
3. 它**不是**旧的 use-after-free——那个崩在**运行中**（docs/34：46 次决策 / 116 个 worker）。
4. docs/34 把退出期 panic 记为「良性，进程本在退出，EXIT 0 不影响」——
   **在本机它并不总是 EXIT 0**，约 1/3 的跑是 139。那句话该收窄。
5. **不能**站住的：把它归因于 `_teardown_slm_worker()`。数据不够。
   （对照跑 `BackendBench.tscn` 也只跑了 1 次得 EXIT 0，同样不构成"它不崩"的证据。）

**本轮【不修】，理由写清楚**：连触发条件都还没定位（间歇、疑似与扩展的退出期线程收线有关），
此时任何修法都是推测性的；而 docs/34 的教训恰恰是「第一版'修复'反而重新引入了它要消灭的 bug」。
**留作专门一轮**：先用上表的两臂各跑 30 次把崩率差做实，再谈修。

**bench 的诚实性处理**：进程看不见自己的 teardown ⇒ 断言 A 本进程判不了。
verdict 已改为「**运行中**断言 PASS」并显式说明 A 由调用方的 exit code 裁决。
**绝不允许出现"打印 PASS 而进程段错误"的组合**——一次绿的 exit code 也不构成证据，这东西是间歇的。
