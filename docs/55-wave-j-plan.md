## 〇、这一波的由来：一条红线和一次实测对不上

`docs/41 §0` 红线 #3 **逐字**写着：

> **消费级硬件（含手机）：出货目标是最多 60 居民、骁龙 8 Elite 级手机。**

而 I3 实测（docs/54）：

| N | #40 红/12 | 逐 seed 最差货满足率 |
|---|---|---|
| 12（CI fixture） | 0/12 | 0.615 … 0.889 |
| **16** | **2/12 ❌** | 0.407 0.490 0.514 … |
| 60（**红线上的出货目标**） | 12/12 | **0.048 … 0.147** |

N=60 时**屋瓦期末库存 = 0、断供 60/60 天，12/12 个 seed**。

⇒ **产出系统（E1 → F1 → G3）从头到尾是在 N=12 上设计与标定的，
而没有任何一步拿它对过项目自己的出货目标。**
这不是调参问题，是**红线与实测不符**。软门在 **N=16** 就破——出货 fixture 离边缘约 4 个居民。

**本文不替这件事做决定**：它有好几个都说得通的答案（把产出按人口缩放／把镇子规模封顶／
承认产出是 12 人规模的特性并改红线／把满足率判据按 N 分档）。**决定要走一次外部对抗评审**，
理由是它不是"哪个数对"，而是"这个项目要什么"。评审结论回来之前，**不要有人去动 `production.json` 的数**。
