# 42 · 位置伪影还是能力天花板：把出货那一份 prompt 原样喂给大模型

**2026-07-26。离线 prompt 级实测，RTX 4090（WSL2）+ llama.cpp server（ghcr.io/ggml-org/llama.cpp:server-cuda）。**
数据集 = 本项目自己的仿真在 `backend=null` 下跑出的 **5290 个真实决策点**（8 seed × 8 天 × N=12，与 docs/38 同一网格）。
所有臂看**同一批 prompt**、走**同一条接受规则**、对**同一套判据**（docs/36 §4 的四条）与**同一组零假设**。

---

## 〇、这一棒要杀死的那个假设

docs/36 / docs/38 / docs/40 三连测得出一个负结果：出货的 1.5B **改变**决策、但与"均匀瞎猜"统计不可区分，
且在真出货配置下只驱动全镇 **0.04%** 的决策。路线图上剩下的杠杆写着"**蒸馏一个学生模型给选择以方向**"。

**但 docs/38 §4.2 留下一个更便宜、也更危险的可能**：那张选号直方图是**位置**的——
`index 0` 在 3285 次落地里**一次都没被选过**，30.5% 压在 `index 3`。
一个 3285 发不中 0 号的模型，看起来不像"判断力弱"，像**任务编码坏了**。
如果编码是坏的，**蒸馏只会把一个坏任务忠实地蒸下去**——那是很贵的一种保留 bug 的方式。

所以先花半天把这一问结掉：**把游戏真正在用的那一份闭集选号 prompt，一字不改地喂给一个大得多的模型。**

**结论提前说（两条都成立，而任务书假定它们互斥）：**

1. **编码没坏。** 大模型在**完全相同**的 prompt 上，名次 0.495→**0.276**、效用保住 0→**+54%**、
   格式合规 **100%**，8/8 seed 同向（p=0.0078）。**这份 prompt 是可读的，读得懂的模型就能读懂。**
2. **1.5B 的塌陷是真的，而且确实是编码交互的伪影。** 洗牌实验把两个模型的**守恒量**分开了：
   31B 守**内容**，1.5B 守**位置**。系统 prompt 里那个字面示例「如 **3** 或 A」和字符 `0` 本身各自被量化了。
3. **但修编码买不到判断力。** 把 1.5B 的编码病一个一个治掉（去示例 / 换字母表 / 洗牌），
   选 0 号率能从 0.0000 恢复到 0.137（≈随机基线 0.130），**而名次纹丝不动地停在 0.46–0.50（=随机）**。
4. **塌陷的门槛在 1.5B 与 3B 之间，而代码本来就默认用 3B。** 同族梯级（0.5B→1.5B→3B→9B→31B）上，
   选 0 号率是 0.13% / **0.00%** / 18.4% / 16.8% / 22.1%，合法率 96.1% / **85.1%** / **100%** / 99.9% / 100%。
   `AIBackend.slm_model_path` 的默认值**已经是** `qwen2.5-3b-instruct-q4_k_m.gguf`，
   但真机走的是另一条解析分支、装的是 1.5B —— **docs/36/38/40 测的是一个代码并不想用的模型。**

**净判决：能力天花板确认；蒸馏的前提条件（存在一个在这项任务上确实胜任的教师）现在被实测坐实了。
但蒸馏已经不是最便宜的下一步——换成代码本来就默认的 3B（零训练）能同时拿掉"格式不遵从"和"跳过维生动作"两条（§6.1）。
另外发现一条 CI 结构上查不到、且与能力无关的产品破损机理（§5）。**

## 一、方法：三件必须先做对的事

### 1.1 ★ 数据集必须是【出货那一份】——为什么没能复用 `bench/log_decisions.gd`

契约红线 #5 要求先找现成的。**找了，两个都不能直接用，原因值得写进档案：**

| 既有件 | 为什么不够 |
|---|---|
| `bench/DistillDump.gd` | 只导 `sys/user/候选标签`，**不导 `score`、不导引擎基线** ⇒ docs/36 那四条判据一条也算不出。且去重键是 `人设\|标签集\|时段桶`，样本**不代表**决策点分布。另：仓库里已提交的 `bench/distill_contexts.jsonl` 是**过期**的——里面还是老的 JSON schema prompt（`{"pick":…,"speech":…}`），**不是**现在出货的闭集选号 prompt。谁信了那个文件，研究的就是一份游戏早已不用的 prompt。 |
| `bench/log_decisions.gd` | 字段几乎全对（含逐候选 `score`、`cap_order`、`pick_in_cap`、成品 prompt），**但它的 `_cap_order()` 总是把候选按 `score` 降序重排再建 prompt**。而出货路径 `AIBackend._cap_for_llm()` 在 `\|C\| ≤ 36` 时**原样返回**（保持引擎枚举序）。本数据集里 **98.15%** 的上下文 `\|C\| ≤ 36` ⇒ **出货 prompt 几乎从不排序**。对一篇研究位置塌陷的报告，"先把最优解排到 0 号位再问模型"会让结论整个反过来。 |

所以新写了 `game/bench/PickCtxDump.gd`（+ `.tscn`），走 **scene 模式**直接调 **AIBackend 的真函数**
（`_system_prompt` / `_cap_for_llm` / `build_prompt`）——**零重实现、零漂移**。
（`log_decisions.gd` 与 `dump_decide_prompt.gd` 里那两份 prompt 都是 `--script` 模式下的**手抄件**，抄的那一刻就已经和本体分叉了。）

**零扰动（红线 #1）**：采集挂在既有的 `Sim.decision_sink`（`Sim.gd:242`，只读、不抽 RNG、不进 digest）；
唯一额外求值的是"引擎在冻结闭集上的基线" `Sim._logic_decide(ag, capped)`，它会**再次触发 sink** ⇒
**先摘钩子、读完原样还原**（与 `AIBackend._shadow_compare` 同一手法）。全程 `backend = null`。
**CI 全绿、金标零位移**（§10）。

### 1.3 ★ 剂量这个混淆项被设计消掉了，不是被配平了

docs/38 花了整整一节做"解码时延模拟"来配平剂量，因为在线臂里 `slm` 只驱动 62% 的落地决策。
**本文是离线 prompt 级研究：每条臂看的是同一批 800 个 prompt，剂量逐条相同、按构造相等。**
串行 worker、`_wait`、墙钟截止线全部不在图里。

这有代价，必须明写：**本文测的是"给定被问到，模型选得怎么样"，不是"模型会改变小镇成什么样"。**
后者是 docs/38 的问题，本文不重复回答（§7-1）。

### 1.4 量具：docs/36 §4 的四条判据，逐行从 `_shadow_compare` 移植

不是照 docs 复述，是对着 `AIBackend.gd:669-731` 一行一行搬进 `tools/b21_pick_eval.py`：

| 判据 | 定义 | 复读机 | 掷骰子 |
|---|---|---|---|
| ① 归一化名次 | `#{j: s_j > s_pick} / (n-1)` | 0 | 0.5 |
| ② 效用保住率 | `1 − Σ(s_base − s_pick) / Σ(s_base − mean s)` | 1 | 0 |
| ③ 换动作种类率 | 实测 vs 逐上下文精确期望 | ≈0 | =期望 |
| ④ Δ/L | 选择 ≠ 引擎在同一冻结闭集上的选择 | ≈地板 | `1 − mean(1/\|C\|)` |

接受规则是 `AIBackend.parse_decision` 的**忠实移植**（fail-closed：首字符是合法编号、且其后无任何 ASCII 字母/数字才算数；
否则退 JSON `{"pick":N}` 兼容路；再否则 `parse_fail` → 游戏里走引擎地板）。

**两条零假设都是解析算出来的、不是蒙特卡洛模拟的**（逐上下文求期望再平均），
所以下表里"随机"那一行**没有采样噪声**：

| | 名次 | 效用保住 | 换种 | Δ | 选 0 号 |
|---|---|---|---|---|---|
| **均匀随机零假设** | **0.495** | **0.000** | 0.840 | 0.870 | **0.130** |
| **鹦鹉地板**（argmax） | **0.000** | **+1.000** | 0.016 | 0.081 | 0.128 |

统计一律 **8 个配对 seed 的精确符号置换检验**（2⁸=256 全枚举，双尾），与 docs/38 同口径。
**n=8 时最小可能 p = 0.0078 = 8/8 seed 同向；任何 "ns" 只能读作"本网格分辨不出"。**

## 二、模型选择与许可

24 GB 显存是硬约束。选了 **`gemma-4-31B-it-QAT`（Q4_0，17.6 GB）** 作为"大得多的模型"：

* **参数量约为出货模型的 20 倍**，且**是另一个家族**——这一点是刻意的：
  如果**换了 tokenizer、换了 chat template、换了训练数据**的模型在**同一份 prompt** 上依然读得懂，
  那"编码本身不可读"这个假设就被杀得比同族对照更彻底。
* QAT 权重 ⇒ 4-bit 下质量损失小；纯 GPU 常驻（实测 20.2 GB 显存，2.4 req/s）。
* 同时跑了一条**同族能力梯级**做剂量-反应：`qwen2.5-0.5B / 1.5B / 3B`（全部 q4_k_m，与出货同量化）+ `Qwen3.5-9B`（q4_k_m）。
  **梯级只跑了 `nat` + `shuf` 两个条件**（八条件全消融只在 1.5B 和 31B 上跑了，见 §8-9）。
* **1.5B 用的就是出货那一份权重文件** `qwen2.5-1.5b-instruct-q4_k_m.gguf`（与 docs/36/38 同一个），
  从本机模型库经 LAN 拷过去，**不是**重新下载的另一份。

**许可**：本轮**只做评测**，不训练、不蒸馏、不分发权重，**没有任何权重进仓库**（红线 #4；CI step 0 对整棵已跟踪树把关）。
Gemma 系列的使用条款允许评测用途；Qwen2.5 的 0.5B/1.5B 为 Apache-2.0。
**若将来真要拿 31B 当蒸馏教师，许可需要重新审一遍——评测的宽松不自动延伸到蒸馏。**（本文不做那一步。）

**一个必须交代的自伤**：第一次跑 31B 得到"合法率 0%"，我差点把它写成"大模型也读不懂"。
真相是这个模型带 reasoning channel，`max_tokens = 8`（= 出货的 `DECIDE_MAX_TOKENS`）把答案截在了思考通道里
（首 token 恒为 `<|channel>`，概率 0.9999）。加 `--jinja --reasoning off --reasoning-budget 0` 后立刻正常。
**"大模型也塌了"这个结论差一点是被我的工具链生产出来的。**

## 四、★ 位置塌陷的直接诊断

### 4.1 洗牌把两个模型的【守恒量】分开了

同一批上下文，只把喂给模型的候选**重排**（内容一字不动），看**什么东西不变**：

| | | 选中的**自然下标**直方图（top-4） | 选中的**槽位**直方图（top-4） | 选槽位 0 |
|---|---|---|---|---|
| **1.5B** | `nat` | **3:204** 5:131 6:117 7:65 | **3:204** 5:131 6:117 7:65 | **0.0000** |
| | `shuf` | 0:91 2:83 5:67 3:66（**摊平**） | **3:215** 6:90 5:79 11:67（**不变**） | **0.0000** |
| | `rev` | 0:113 2:95 1:86 4:83（**摊平**） | **3:196** 6:117 5:69 7:65（**不变**） | **0.0000** |
| **31B** | `nat` | **0:177** 2:125 3:86 7:58 | 0:177 2:125 3:86 7:58 | 0.2213 |
| | `shuf` | **0:162** 2:126 1:77 3:77（**不变**） | 1:110 0:103 3:98 2:90（**摊平**） | **0.1288** |
| | `rev` | **0:149** 2:121 1:88 7:66（**不变**） | 0:184 1:85 3:77 6:65 | 0.2300 |

**完美对偶：**

> **1.5B 守的是位置**——不管 3 号槽里坐着谁，它都答 3；不管 0 号槽里坐着谁，它一次都不答 0。
> **31B 守的是内容**——不管那个候选被挪到哪个槽，它都还挑它；它对**槽位** 0 的偏好在洗牌后正好落回随机基线 0.130。

判据侧同样干净：**31B 的名次在洗牌下纹丝不动**（0.276 → 0.274，p=0.68 ns；效用保住 +0.538 → +0.544，p=0.63 ns），
而 **1.5B 的名次在三种排列下都是随机**（0.480 / 0.461 / 0.479）。

### 4.2 首 token 分布：`'0'` 的概率是 1.6 × 10⁻⁴

采样直方图只看得见峰顶；把 1.5B 的**首 token top-20 logprobs** 取出来（只统计 `|C| ≥ 12` 的 310 个上下文，
这样 0–9 全都是合法编号，比较才公平）：

| token | 平均概率质量 | argmax 次数 |
|---|---|---|
| `'5'` | 0.2125 | 73 |
| `'6'` | 0.1829 | 59 |
| `'3'` | 0.1178 | 39 |
| `'A'` | 0.1112 | 35 |
| `'7'` | 0.1038 | 35 |
| `'2'` | 0.0185 | 3 |
| `'9'` | 0.0052 | 1 |
| `'1'` | 0.0021 | 1 |
| **`'0'`** | **0.00016** | **0 / 310** |

均匀应当是 ≤ 0.083。**模型给 `'0'` 的概率比均匀低约 500 倍**，而 `'5'/'6'` 高 2.5 倍。
这是一个**以 3–7 为中心的单峰小数字先验**，和候选里是什么毫无关系。

### 4.3 prompt 消融：两个编码病各自被量化了

出货的系统 prompt 原文是：

> 你是像素小镇的居民。从下面【候选】里挑一个此刻最想做的行动，只回它的【编号】（一个字符，**如 3 或 A**），别回任何其它字。

**那个「如 3」是字面写死的示例编号。** 而 docs/38 量到 30.5% 的答案压在 index 3。逐条拆开（1.5B，800 上下文）：

| 条件 | 改了什么 | 合法率 | **名次** | 效用保住 | **选 0 号** | 峰值下标 |
|---|---|---|---|---|---|---|
| `nat`（出货） | — | 85.1% | 0.480 | +0.029 | **0.0000** | **3 (30.0%)** |
| `nat_t0` | 贪心解码（temp 0） | 87.0% | 0.491 | −0.002 | **0.0000** | **3 (30.9%)** |
| `nat_noex` | 删掉「如 3 或 A」 | 85.0% | 0.496 | −0.013 | 0.0015 | 6 (29.0%) |
| `nat_ex0` | 示例改成「如 **0** 或 A」 | 80.6% | 0.471 | +0.053 | **0.0357** | 6 (26.0%) |
| `nat_letters` | 编号改成 **A-Z**（内容/顺序不动） | 79.1% | 0.477 | +0.054 | **0.1374** | 3 (26.5%) |
| `nat_1based` | 编号改成 **1-9,A-Z,0** | 80.2% | 0.481 | +0.032 | 0.0047 | — |
| `shuf` | 候选洗牌 | 87.0% | 0.461 | +0.076 | 0.1307 | — |
| — 随机零假设 | | 100% | **0.495** | **0.000** | **0.1297** | — |

**三条可下的结论：**

1. **「index 3 的堆」有相当一部分就是系统 prompt 里那个字面示例造成的。**
   删掉示例 → index 3 的质量从 204 掉到 78；把示例换成 0 → 选 0 号率从 **0.0000 涨到 0.0357（×24）**。
   **一个写来帮模型的例子，把三成的决策焊死在了一个候选位上。**
2. **「从不选 0」主要是字符 `'0'` 的问题，不是位置 0 的问题。** 只把编号字母表换成 A-Z（**候选顺序一字不动**），
   选首位的比例从 **0.0000 直接跳到 0.1374**——**与随机基线 0.1297 不可区分**。病灶是那个 token。
   （`nat_1based` 里首位标成 `'1'` 仍只有 0.0047 ⇒ 模型躲的不只是 `'0'`，是**小数字整体**；峰在 3–7。）
3. **★ 但每一条治好之后，名次和效用都没有动。** 八个条件的名次是 **0.461–0.496**，随机是 **0.495**；
   效用保住率是 **−0.013 ~ +0.076**，随机是 **0.000**。
   **把格式病全部治光，模型依然在瞎猜——只是换了一种更均匀的瞎猜法。**

**同样八个条件在 31B 上：名次 0.265–0.297、效用保住 +0.501~+0.564、合法率恒 100%、选 0 号 0.186–0.254。**
**把 1.5B 拨动 100 倍的那些旋钮，对 31B 的效果小到测不出。**（`shuf` vs `nat`：名次 p=0.68 ns。
唯一显著的是 `nat_letters` 让名次从 0.276 微劣化到 0.290，p=0.016——**效应量 0.014，方向正确、大小可忽略**。）

## 五、★ 一个顺带被解释掉的产品破损：为什么模型会把人饿穿

docs/38 §5 报了一条 CI 结构上查不到的破损：`slm` 臂 **8/8 seed 违反硬不变量 #01（无饿穿）**，
而同剂量同迟疑的 `mock` 是 0/8 ——"是**选择**把人饿穿的，不是**等待**"。当时没有机理。

**机理在这里：`index 0` 有 74.84% 的时候是【吃饭】或【睡觉】。**

（自然枚举序 = 对象候选在前、社交候选在后；对象候选里排最前的正是维生对象。
逐条统计：index 0 的动作构成 = 吃饭 2372 / 睡觉 1587 / 闲聊 610 / 歇着 477 / …）

于是"从不答 0"直接等价于"**系统性跳过维生动作**"。选中动作里维生动作（吃饭+睡觉）的占比：

| 臂 | 维生动作占比 |
|---|---|
| **`gemma-4-31B`（nat）** | **42.1%**（比引擎还高） |
| `gemma-4-31B`（shuf） | 42.2% |
| 引擎地板 `logic` | **36.9%** |
| `Qwen3.5-9B`（nat） | 32.7% |
| `qwen2.5-3B`（nat） | 31.2% |
| `qwen2.5-1.5B`（shuf） | 20.5% |
| `qwen2.5-1.5B`（letters） | 20.1% |
| — 均匀随机零假设 | **18.5%** |
| **`qwen2.5-1.5B`（nat，docs/36-40 测的那一档）** | **4.8%** |
| `qwen2.5-0.5B`（nat） | 4.3% |

**1.5B 在出货 prompt 下只有 4.8% 的选择是吃饭或睡觉——比瞎猜低 4 倍，比引擎低 8 倍。**
只要洗一下牌（内容不动）就回到 20.5%（≈随机）；只要把编号换成字母就回到 20.1%。
**这条链是完整的：字符 `'0'` 的先验 → 从不选 0 号槽 → 系统性跳过维生对象 → 饿穿。**

**而且它精确地只发生在会塌陷的那两级**（0.5B 4.3% / 1.5B 4.8%）；3B 起就回到 31–42%，**≥ 随机、逼近引擎**。

> **这解释了 docs/38 §5，也顺带说明它不是"模型太笨"的必然后果**：`shuf` 档同样笨（名次 0.461，与随机不可分），
> 但维生占比回到随机水平。**饿穿那一条是格式病，不是能力病。** 这两件事第一次被分开了。

## 七、判决与建议

### 7.1 判决

* **编码病理：成立，但不是"prompt 不可读"。** 大模型在**同一份未改动的 prompt** 上做出了明显优于随机的选择
  （8/8 seed，p=0.0078）。**"任务编码坏到没模型能做"这个假设被证伪。**
* **能力天花板：成立。** 1.5B 在**八种**不同编码下、在**去掉一切在线混淆项**的离线设定下，
  名次恒在 0.46–0.50、效用保住恒在 0 附近。**编码不是它的瓶颈，它自己是。**
* **两者不互斥**（任务书假定它们互斥，见 §8-6）：1.5B 的**具体失败模式**由编码决定
  （答 3 不答 0 → 跳维生 → 饿穿），而它的**天花板高度**由能力决定。

### 7.2 蒸馏现在是否被许可？——**是，但它已经不是最便宜的下一步**

**前提条件被坐实了：存在一个在【这项确切任务、这份确切 prompt】上确实胜任的教师。**
这正是本轮之前**没有**的证据——docs/36/38/40 只证明了学生不行，没证明这题**可做**。现在证明了：
名次 0.276、效用保住 +54%、合法率 100%、8/8 seed 同向。

**但本文同时挖出两条比蒸馏便宜得多、且必须排在蒸馏之前的杠杆：**

* **① 换成代码本来就默认的 3B**（§6.1）：合法率 85%→100%、效用保住 +0.03→+0.22、饿穿机理消失。
  **零训练、零标注、改一个文件路径。** 代价是解码时延（本文没测）。
* **② 修 prompt 的两个字符串**（§7.3）：把示例编号「如 3」和 `0-9` 编号字母表治掉。
  **零训练。** 收益是去掉"系统性跳过吃饭睡觉"这个 bug（不是加判断力）。

**这两条做完再谈蒸馏。** 若仍要蒸馏，三条约束必须写进任务书：

1. **★ 先修 prompt，再采标签。** 如果拿现在这份 prompt 去让教师标数据，教师会照样把维生动作排在 `0` 号位——
   **然后学生会把"0 号位是维生动作"和"永远别答 0"一起学走**。§4.3 已经证明学生对编号字母表极度敏感。
   **蒸馏前必须先把编码病去掉，否则等于花钱买一个继承了 bug 的学生。**
2. **教师不是本文这个 31B 也行，但必须在同一套判据上先过一遍。** 备忘录里写的 bake-off 教师
   （Nemotron-3-Super-120B-A12B）**装不进 24 GB**，本轮**没测过它**——不要假定它的读数与本文的 31B 相同。
   另：拿 31B 当**蒸馏**教师需要重新过一遍许可（§2）。
3. **蒸馏的天花板是 §3 那一行，不是 100%。** 教师自己也只保住 54% 的效用、只走完一半路。
   **学生不可能超过教师**，且要塞进手机还得再降一个量级。**在动手前先算清楚："54% × 蒸馏损耗 × 0.04% 的决策占比"值不值这个电量。**
   docs/40 那条 0.04% **本文完全没有改善**——本文只证明了"被问到时能选得更好"，没证明"能被问到更多次"。

### 7.3 ★ 一条比蒸馏便宜两个数量级的修法（**建议，本棒按契约不实现**）

§4.3 + §5 指出的三处，改动都在 `AIBackend.gd` 的**两个字符串**里，不碰仿真、不碰 digest：

1. **把系统 prompt 里的字面示例编号删掉或改成非编号占位**（`_system_prompt()` 的「如 3 或 A」）。
   实测：删掉 → index-3 的堆掉 62%；改成「如 0」→ 选 0 号率 ×24。
2. **把闭集编号字母表从 `0-9/A-Z` 换成 `A-Z`**（`_idx_label` / `_label_idx`，两个函数一起改，
   `parse_decision` 的 fail-closed 规则不用动）。实测：选首位率 0.0000 → 0.1374（= 随机基线）。
   **注意这会把可编号候选上限从 36 降到 26**，`_cap_for_llm` 的 36 要跟着改，是**会移动模型路径行为**的改动。
3. **（可选）给喂模型的那份候选列表逐次洗牌。** 引擎侧本来就是候选顺序无关的
   （`_cand_salt` 取候选身份而非下标，`cand_permute` 就是机检这条性质的）⇒ **只洗喂模型的那一份，引擎基线一字不动**。

**预期收益要说实话**：这三条**买不到判断力**（名次仍是 0.46–0.50，§4.3 结论 3），
它们买到的是**去掉"系统性跳过吃饭睡觉"这个 bug**，也就是 docs/38 §5 那条硬不变量破损。
**这是修 bug，不是加能力**——但它比蒸馏便宜两个数量级，而且**必须在蒸馏之前做**（见 7.2-1）。

> 按 brief 要求：**本棒只写建议，不实现**。上述任何一条落地都会改变模型路径行为，
> 需要按 docs/38 §八-2 的思路先补一条**确定性**的模型路径守门（`--backend random --decode-ticks K` 冒烟），
> 否则又是一次"CI 全绿而产品已破"。

## 八、这个数【没有】回答什么

1. **本文是离线 prompt 级研究，不是世界级反事实。** 没有跑任何一局用 31B 驱动的仿真，
   所以**没有**任何 PI / 熵 / 人均动作种类 / 戏剧事件 / 真实饿穿计数的读数。§5 的饿穿机理是
   **"选中动作构成"这一个中间量**上的证据，不是重跑 docs/38 那张表。**要坐实必须真跑一局。**
2. **`score` 仍然是启发式，不是真值。** 本文全部四条判据都对着引擎自己的效用函数。
   docs/38 §〇 说得对：**偏离引擎最优本身不是罪状**，本项目对决策路径的原始意图是风味与多样性。
   所以本文准确的说法是：**31B 与引擎的偏好高度一致，1.5B 与任何东西都不一致。**
   "31B 会让小镇更好玩"**本文没有证据**。
3. **没测教师质量的上界。** 只测了一个 31B。更大的模型（备忘录里的 120B teacher）**装不进 24 GB，本轮没跑**。
4. **没测端上可行性。** 31B 是 4090 上 2.4 req/s；出货目标是骁龙 8 Elite。本文与"手机上跑什么"完全无关。
5. **`gemma-4-31B` 是跨族对照，也因此引入了跨族差异**（tokenizer / chat template / KV 量化 q8_0）。
   它读得懂 ⇒ "编码不可读"被证伪，这个方向是稳的；但**"31B 比 1.5B 强多少"里混着家族差异**，不是纯规模效应。
   同族梯级（§6）是用来补这一条的。
6. **单次生成、单套采样参数。** 主档 temp=0.7（对齐 `_fire_http`），另跑了贪心档（`nat_t0`）做敏感性——
   两档结论一致（1.5B 名次 0.480 vs 0.491，选 0 号都是 0.0000）。**没有做多次重采样求方差。**
7. **NobodyWho 的真实采样参数没有对齐。** 出货的 slm 路走 `NobodyWhoChat.ask()`，用的是扩展默认采样器；
   本文走 llama-server 默认采样器 + temp 0.7。**贪心档结论不变**说明这不是驱动因素，但严格说这两者没有逐参数对齐。
8. **`crisis` 状态在本网格上恒为 0。** N=12 × 8 天 × logic 地板不会把人饿到危机线，
   所以**本数据集里没有任何"危急决策"样本**——那恰恰是最该考察判断力的一档，**本轮没有覆盖**。
9. **梯级模型只跑了 2/8 个条件。** `0.5B / 3B / 9B` 只有 `nat` + `shuf`；
   八条件全消融只在 `1.5B` 和 `31B` 上做过。所以"塌陷门槛在 1.5B 与 3B 之间"是**基于 `nat` 的选 0 号率**下的结论，
   **没有**在 3B 上验证"删掉示例编号会不会把它的直方图也推走"。这是本轮最该补而没补的一格。
10. **3B 的真机代价完全没测**：时延、落地率、FPS、电量、Native Heap 一个都没量。
   §6.1 的建议**只在"被问到时选得怎么样"这一个轴上成立**。
11. **`gemma-4-31B` 的 KV cache 用了 q8_0 量化**（24 GB 装不下 fp16 KV），其它模型是 fp16。
   单 token 答案上这个差别应当可忽略，但**没有做 fp16-KV 的对照**。

## 九、这份任务书 / 既有文档哪里是错的

契约 §4 要求这一节。以代码与实测为准：

1. **"如果大模型也塌陷 → 编码坏了；如果大模型选得好 → 能力天花板"这个二分是假的。**
   两件事**同时**成立：编码可读（31B 在同一份 prompt 上远优于随机），**且** 1.5B 的失败模式确实由编码决定
   （示例编号"3"、字符 `0`、槽位而非内容）。任务书按互斥写，实测按并存收场。
2. **"the on-device 1.5B … at the real shipping config"——代码默认的不是 1.5B，是 3B。**
   `AIBackend.gd:150` 的 `slm_model_path` 默认 `qwen2.5-3b-instruct-q4_k_m.gguf`；真机之所以跑 1.5B，
   是因为安卓分支 `_resolve_model_path()` **完全绕开** `slm_model_path`、去 `Documents/LivingTown/model.gguf` 取文件。
   **这不是"出货配置"，是"手工放进去的那个文件"。** 而两者的读数差别很大（§6.1）。
3. **"`DistillDump.gd` exports real decision contexts" —— 它导不出打分需要的东西。**
   没有 `score`、没有引擎基线 ⇒ docs/36 那四条判据一条也算不出。
   而且仓里已提交的 `game/bench/distill_contexts.jsonl` 是**过期**的：里面是老的 JSON-schema prompt
   （`{"pick":…,"speech":…,"emotion":…}`），**不是**现在出货的闭集选号 prompt。
4. **任务书没提 `bench/log_decisions.gd`，而它才是最接近的既有件——也埋着这一棒最大的坑。**
   它的 `_cap_order()` 把候选**按 score 降序重排**再建 prompt，而出货路径在 `|C| ≤ 36`（本数据集 98.15%）时
   **保持枚举序**。用它做位置研究会得到相反的结论。
5. **"the parser's accept rule" 不是嫌疑人。** 同一条 fail-closed 规则下 31B / 3B 的合法率是 **100%**。
   1.5B 那 14.9% 的拒绝里绝大多数是它自己答了越界数字（`|C|=2` 时答 `'52'`）。
6. **Δ 地板（鹦鹉地板）实测是 8.64%，不是 docs/36 §3.1 引的 12.7%。** 不矛盾，是**分母不同**：
   docs/36 在 SLM 落地子集上算，那个子集偏向大 `|C|`。任务书说"measure the floor, don't assume it"是对的，
   但**引用别处的地板时也必须问它是在哪个分母上量的**。
7. **docs/36 §4.6 的"选号分布没有塌"读反了。** 它看到"用到 16–36 种下标、选 0 号只占 0.0–1.0%"就排除了退化。
   docs/38 已经纠正过一次；本文把机理补全：**它塌成了一个位置分布，而"0.0%"那一格本身就是最强的信号。**
8. **`hf.co` 从 4090 上不通。** 任务书建议"pip install transformers / 下模型"或"docker -c gpu4090 拉现成镜像"，
   实测 `huggingface.co` 与 `registry-1.docker.io` **都超时**（`ghcr.io`、`pypi`、`hf-mirror` 通）。
   真正省事的路是任务书没提的那条：**本机 `E:\Documents\LM-Studio-Models\` 已有完整模型库**
   （含出货那一份 1.5B 权重），LAN scp 实测 ~95 MB/s，17.6 GB 三分钟到位。
9. **任务书没警告 reasoning-channel 模型。** `max_tokens = 8`（出货的 `DECIDE_MAX_TOKENS`）会把带思考通道的模型
   的答案整个截在通道里，产出"合法率 0%"。**"大模型也塌了"这个结论差一点由我的工具链生产出来**（§2）。
