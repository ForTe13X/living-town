# 36 · 第三次换分母：landed ≠ drove，真影响力是覆写率 Δ/C

**2026-07-26。全部数据为【桌面】实测（Windows / AMD Radeon Vulkan / 本机 CPU），本轮无安卓设备连接。**
真模型 = `qwen2.5-1.5b-instruct-q4_k_m.gguf`，全部 SLM 数字取自 `--realtime`（出货节奏，1 sim-日 = 19.2 s 墙钟，
三个配置实测节奏均为 19.2s，"节奏相符，占比可外推"）。

这是同一个问题上的**第三个分母**。前两个都是我们自己写的、也都被推翻了：

| # | 口径 | 读作 | 结局 |
|---|---|---|---|
| 1 | `landed / fired` ≈ 67–80% | "模型驱动了 2/3 的决策" | ❌ docs/34→35 推翻：分母里没有"忙得根本没发"的那一大片 |
| 2 | `landed / decisions` | "模型做了这么多成决策" | ⚠️ docs/35 立此口径——**但它只是上界** |
| 3 | **`Δ / decisions`（本文）** | "模型**改变**了这么多成决策" | ✅ 本文实测 |

第 2 个分母是外部对抗评审打下来的：**`landed` ≠ `drove`**。
模型"落地"只说明**它给的下标被采纳了**，不说明它改变了任何东西——
闭集里那个分数最高的候选，引擎自己也会挑。一个只会复读引擎偏好的模型，`landed/decisions` 可以是 100%，
而它对小镇的影响是 **0**。

所以真正要量的是**覆写率**：

> **Δ/C** = 在所有落地决策 C 里，模型实际应用的选择与引擎策略**在同一候选集上**会挑的那个**不同**的比例。

**本文结论提前说**：Δ/C 确实不小（15–55%），但**第四节的退化排查表明这些覆写在统计上与"均匀瞎猜"无法区分**，
且模型**没有**保住候选集里的效用。所以本文的净结论是一个**负结果**：
「模型改变了决策」成立；「模型改善了决策」**无证据**。

## 一、三个量的定义（以及它们各自答什么问题）

| 记号 | 定义 | 答的问题 |
|---|---|---|
| **C** | 落地决策数 = `decide()` 调用数 − 思考中(`_wait`)次数 | 全镇一共 committed 了多少次决策 |
| **L** | 模型下标被实际应用的次数（`stats.landed`） | 模型**参与**了几成 → **L/C 是影响力上界** |
| **Δ** | L 中，应用的选择 ≠ 引擎在同一候选集上的选择 | 模型**改变**了几成 → **Δ/C 是真·直接覆写率** |

外加 **Δ/L** = 模型落地时有多爱唱反调。

### 1.1 C 的定义我复核了一遍，没有照抄

对照 `Sim.gd:1084-1095` 的 backend 分支，逐条核 `AIBackend.decide()` 的每一个 return：

| `decide()` 返回 | 出处 | Sim 的动作 | 计入 C？ |
|---|---|---|---|
| `Sim._logic_decide(...)`（非空） | logic/回放/熔断/节流/过载/worker忙 六处早退 | `agent_apply` | ✅ 引擎决策 |
| `{}` | 预算门 / parse 失败 / 候选失效 / 超时 | `_logic_decide` 兜底后 `agent_apply` | ✅ 引擎决策 |
| 非空 intent | 落地路径 | `agent_apply` | ✅ 模型决策 |
| `{"_wait": true}` | `_fire` 后、仍在等 两处 | `return`，下 tick 拿同一 agent 再问 | ❌ 必须剔除 |

`waits` 恰好在且仅在那两个 `_wait` 分支自增 ⇒ `C = calls − waits` 成立。
另注：`_logic_decide` 即便 `cands` 为空也返回带 `say` 键的非空字典，**永远不会**被误判成"放弃"；
而 LOD 节流跳过的 agent 根本不调 `decide()`，正确地不进 C。

## 二、影子基线怎么算的，以及它凭什么不破红线 #1

实现在 `AIBackend._shadow_compare()`，在**落地那一刻**（`stats["landed"] += 1` 紧后）就地对拍：

```gdscript
var base_frozen := Sim._logic_decide(agent, capped)      # 模型看的那个闭集（top-36）
var base_full   := Sim._logic_decide(agent, candidates)  # 本 tick 全量候选
```

比较用 `_cand_key()`（完整动作身份：kind/action/partner/target/subject/need/object/amount/duration），
**不比 `say`/`score`** —— 台词换了不算覆写，动作换了才算。

两个基线各有各的用处：

* **`capped` 口径（Δ，headline）** —— 评审要的"同一冻结候选集"。剔掉了"裁到 36 个"这个混淆项，
  纯粹量**模型 vs 引擎策略**的分歧。
* **`candidates` 口径（Δ_full）** —— 真·反事实分支：模型若返回 `{}`，`Sim.gd:1090` 走的正是
  `_logic_decide(ag, cands)` 全量这一支。

实测两者**在所有配置下完全相等**（N=12 时候选 ≤36 本就同集；N=60 时虽有 928 次裁剪，
但被裁掉的都是低分候选，引擎本来也不会选它们 ⇒ 结论对"裁到 36"这个设计选择不敏感）。

### 2.1 为什么多调一次 `_logic_decide` 不会污染仿真

任务书要我自己验证"`_rng_at` 是无状态的"这个说法，而不是相信它。**我验了，它是无状态的**——
以下三条证据是独立的：

**① 源码：每次调用都新建一个 RNG，种子是纯函数。** `Sim.gd:301-304`

```gdscript
func _rng_at(salt: int, who: int = 0) -> RandomNumberGenerator:
    var r := RandomNumberGenerator.new()
    r.seed = seed_base + tick_no * 911 + salt * 7919 + who * 104729
    return r
```

没有共享实例、没有 `randomize()`、没有"取一个数然后前进"。返回的 RNG 用完即弃，
**调用次数不进入任何后续抽样的输入**。多调一次和不调，逐比特等价。

**② 审计：`Sim.gd` 里没有别的随机源。** 全文搜 `RandomNumberGenerator|randi()|randf()|randomize`
只命中 6 处，全部是 `_rng_at(...).randf()` / `.randi()` 形式（第 302 行是 `_rng_at` 自己的构造）。
不存在一个"全局 RNG"能被额外调用拨动。

**③ 旁证：存档系统本身就赌在这条性质上。** `Sim.gd:845` 的注释写着
「**RNG 无状态（`_rng_at` 纯 f(seed_base,tick_no)）→ 没有 RNG 态要存**」——
`save_game` 因此**根本不序列化任何 RNG 状态**。如果 `_rng_at` 消耗序列态，`save_load_test`
早就该红了。这条性质不是我为了本文新主张的，是既有代码已经依赖了很久的。

**结论：属于任务书说的"无状态"那一档 ⇒ 额外调用安全**，
无需把基线挪到发起前，也无需离线重建 trace。

### 2.2 `_logic_decide` 的其余副作用也逐条堵了

* **不改候选**：函数里 `best` 先 `duplicate()` 再写 `say` ⇒ 原候选字典不被污染。
* **不写 Sim 态、不进 `event_log`/`event_digest`**：函数体只读 `cands`。
* **唯一的外部副作用是 Phase-0 数据集钩子 `decision_sink`**（`Sim.gd:2735`）。
  这是本次唯一需要动手的地方：影子调用期间**显式摘钩子再原样还原**，
  保证即便 `bench/log_decisions.gd` 正在采集数据集，也不会被注入两条幽灵样本。

## 三、实测：Δ/C

4 seed × 8 天，`--realtime`，三个配置节奏实测均为 19.2 s/sim-日（= 出货节奏，占比可外推）。

| 配置 | C（落地决策） | L | **L/C（上界）** | Δ | **Δ/C（真覆写率）** | Δ/L |
|---|---|---|---|---|---|---|
| **N=12 GPU** | 2618 | 1630 | **62.3%** | 1452 | **55.5%** | 89.1% |
| **N=12 CPU** | 2405 | 759 | **31.6%** | 674 | **28.0%** | 88.8% |
| **N=60 GPU** | 15606 | 2519 | **16.1%** | 2371 | **15.2%** | 94.1% |

**Δ/C 只比 L/C 低几个百分点**——因为 Δ/L 高达 87–94%：这个模型只要落地，几乎总是选了个和引擎不一样的东西。
乍看像"模型影响力几乎等于它的参与度"。**第四节会说明这个读法是错的。**

### 3.1 扣掉平局抖动地板后的净值

`_logic_decide` 是 `argmax(score + randf()*0.5)`，分差 <0.5 的候选会被抖动翻转 ⇒
**即便一个完美复读引擎偏好的模型，Δ 也不是 0**。用 `mock`（纯 argmax）实测这个地板：
Δ/L = **12.7%**（N=12）/ **32.0%**（N=60，候选集更大 ⇒ 近似平局更多 ⇒ 地板更高）。

按各配置自己的 L 折算出"纯抖动应得的 Δ"，再从实测 Δ/C 里扣掉：

| 配置 | 实测 Δ/C | 抖动地板 | **净 Δ/C** |
|---|---|---|---|
| N=12 GPU | 55.5% | 7.9% | **47.6%** |
| N=12 CPU | 28.0% | 4.0% | **24.0%** |
| N=60 GPU | 15.2% | 5.2% | **10.0%** |

> **复现本测量的人请注意：报 Δ 必须扣这个地板，否则会系统性高估模型影响力。**
> 地板随候选集规模变化，不是常数，必须用同配置的 `mock` 对照现测。

### 3.2 L/C 随 N 塌下去，Δ/C 跟着塌

N 从 12 → 60，分母涨 6 倍（2618 → 15606 次决策 / 32 sim-日），而串行 worker 的墙钟吞吐不变
⇒ L/C 62.3% → 16.1%，Δ/C 55.5% → 15.2%。这条与 docs/35 §1.2 的串行天花板论证一致。
CPU 解码更慢 ⇒ N=12 下 L/C 就已经从 62.3% 掉到 31.6%。

## 四、★ 退化排查：这些覆写与"均匀瞎猜"无法区分

这一节是本文最重要的部分，因为**一个高 Δ/C 本身是可以毫无价值的**。

设想两个极端模型：
* **复读机**（总挑引擎会挑的那个）→ Δ ≈ 0（只剩抖动地板）。影响力为 0，但至少无害。
* **掷骰子**（在候选集里均匀瞎猜）→ Δ/L = 1 − mean(1/|C|)，在本项目的候选集规模下**逼近 85–93%**。

**掷骰子的 Δ 极高。** 所以"Δ/C = 55%"这句话在没有随机基线的情况下**不可解读**。

### 4.1 四条判据（后三条对着引擎自己的效用函数 `score`）

`score` 是引擎的效用函数——`_logic_decide` 就是 `argmax(score + 抖动)`。
拿模型的选择去对 `score`，就能把"有主见的分歧"和"随机的分歧"分开：

| 判据 | 复读机 | 掷骰子 | 读法 |
|---|---|---|---|
| **Δ/L** vs 随机基线 `1 − mean(1/\|C\|)` | ≈0 | ≈基线 | 贴着基线 ⇒ 与随机不可分 |
| **① 归一化分数名次** | 0 | 0.5 | 模型有没有偏好高分候选 |
| **② 效用落差** vs 随机期望落差 | 0 | =随机 | 模型放弃了多少效用，比随机少吗 |
| **③ 换动作种类率** vs 随机期望 | ≈0 | =随机 | 覆写是不是只等于随机换个动作 |

② 和 ③ 的"随机期望"都是**精确算出来的、不是模拟的**：
对每次落地决策，随机挑一个的期望效用 = 候选集 `score` 的均值；
期望换种率 = 候选集中动作种类与引擎基线不同的**比例**。逐次累加取均值即可。

### 4.2 先用 `mock` 标定量具（已知答案的复读机）

`mock` = 纯 `argmax(score)`。它跑出来必须贴着上表"复读机"那一列，否则说明量具本身坏了。

| 判据 | 复读机应有 | `mock` N=12 | `mock` N=60 |
|---|---|---|---|
| Δ/L vs 随机基线 | ≈0 vs 高 | **12.7%** vs 84.5% | **32.0%** vs 92.3% |
| ① 归一化名次 | 0 | **0.017** | **0.012** |
| ② 效用落差 | 0 | 0.386 vs 随机 13.473 ⇒ **保住 97.1%** | 0.238 vs 10.348 ⇒ **保住 97.7%** |
| ③ 换动作种类 | ≈0 | **6.1%** vs 随机 82.0% | **6.3%** vs 随机 80.0% |

**量具通过标定**：它有能力把"贴合引擎偏好"读出来（保住 97% 效用、名次 0.01）。
所以它对 SLM 的读数是可信的。

### 4.3 SLM 的读数：四条判据【全部】落在随机侧

| 配置 | Δ/L | **随机基线**（该配置自算） | 差 | ① 名次 | ② 效用 | ③ 换种 实测/随机 |
|---|---|---|---|---|---|---|
| **N=12 GPU** | 89.1% | **88.1%** | +1.0 pt | **0.543** | 放弃 31.4 vs 随机 28.2 ⇒ **−11.2%** | 88.3% / 85.9% |
| **N=12 CPU** | 88.8% | **89.4%** | −0.6 pt | **0.515** | 放弃 18.9 vs 随机 18.7 ⇒ **−0.6%** | 87.6% / 87.0% |
| **N=60 GPU** | 94.1% | **92.8%** | +1.4 pt | **0.412** | 放弃 13.1 vs 随机 12.5 ⇒ **−5.1%** | 81.3% / 82.1% |

（随机基线按各配置自己的 mean|C| 现算：11.2 / 12.0 / 22.3 个候选，**不是**一个全局常数。）

**四条判据一致落在"与均匀瞎猜不可分"那一侧：**

1. **Δ/L 与随机基线相差 ≤1.4 pt**（对照：mock 低于基线 60–72 pt）。
2. **① 名次 0.41–0.54，随机是 0.50**（对照：mock 是 0.012–0.017）。
3. **② 效用落差全部是负的**——模型放弃的效用**比随机挑一个还多 0.6–11.2%**
   （对照：mock 保住 97%）。**它不但没有保住效用，还略差于随机。**
4. **③ 换动作种类率与随机期望相差 ≤2.4 pt**（对照：mock 6% vs 随机 80%+）。

### 4.4 ① 和 ② 方向不一致，怎么读

N=60 的名次 0.412 略优于随机的 0.5，但效用落差反而**差于**随机 5.1%。这两件事不矛盾：
名次是**序数**、效用是**基数**。若模型系统性避开最差的那几个（序数名次改善），
同时也避开最好的那几个（而高分候选携带了绝大部分效用质量），
在偏斜的分数分布下就会出现"序数略好、基数更差"。

**净读法：序数轴上与随机不可分（0.41–0.54），基数轴上等于或略差于随机。两条轴都不支持"模型在保住效用"。**

### 4.5 所以这准确地许可什么结论、不许可什么结论

**许可：**
* 模型**改变**了 10–48%（净）的落地决策——覆写是真实发生的，不是测量假象。
* 这些覆写**绝大多数换掉了动作种类**（占 Δ 的 86–99%），所以它们在行为层面是可见的，不是换汤不换药。

**不许可：**
* ❌ **不能说"模型改善了决策"。** 四条判据全部落在随机侧，且效用落差略差于随机。
* ❌ **不能说"模型在行使判断力"。** 在本硬件 / 本模型 / 本 prompt 下，
  它的选择**在统计上与"从候选集里均匀抽一个"无法区分**。
* ❌ 不能说"多样性 = 好"。本轮**没有**测过任何"多样性对玩家体验更好"的证据。

**这是一个负结果，本项目明确接受负结果（docs/13 / docs/31 满是被撤回的结论）。**
它不否定端上 SLM 这条路，但它把举证责任放回原处：
**要主张模型在改善小镇，必须先拿出一条它跑赢随机基线的证据。目前没有。**

### 4.6 一个补充观察：选号分布没有塌

`选 0 号` 只占 0.0–1.0%，用到的不同下标有 16–36 种，平均选中下标 4.5–7.5。
所以**这不是"总答同一个号"式的退化**——模型确实在候选集里到处选，
它只是选得**没有方向**。这两种退化不一样，本轮排除了前者、坐实了后者。

## 五、附带修正：`bad_parse` 一直把"世界变了"记在模型头上

排查中发现一个**既有的度量缺陷**（不是本次引入的）：`stats["bad_parse"]` 同时统计了两件完全不同的事：

1. **格式不遵从**（`parse_decision` 返回 `{}`）——脏串 / 越界 / prose，**这是模型的锅**。
2. **候选失效**（P1-1 重验落空，`AIBackend.gd` 的 `chosen.is_empty()` 分支）——
   模型输出**完全合格**，但等待期间世界变了、它选的候选已不存在。**这不是模型的锅。**

本次把两者分账（`parse_fail` / `stale_cand`），实测：

| 配置 | fired | 合法率(旧口径) | **格式不遵从(模型的锅)** | **候选失效(世界的锅)** |
|---|---|---|---|---|
| N=12 GPU | 1921 | 84.9% | **13.7%** | 1.4% |
| N=12 CPU | 1006 | 75.6% | **19.4%** | 5.0% |
| N=60 GPU | 3231 | 78.1% | **7.5%** | **14.5%** |
| `mock` N=12（对照） | 1976 | 92.0% | **0.0%** | 8.0% |

**要点：**
* `mock` 永远输出合法编号，它的"不合法"**100% 是候选失效**——这直接证明旧口径把世界变化算进了模型的格式能力。
* **N=60 下，看起来像模型失败的那 21.9% 里，有三分之二（14.5/21.9）其实是候选失效**：
  镇子越大、决策越密，等待期世界变得越快，模型合格的答案越容易过期。
* 因此**「1.5B 有 20–36% 的格式不遵从率」这个说法偏高，应予更正**：
  本轮实测真实格式不遵从率是 **7.5%–19.4% of fired**，且随 N 增大而**下降**
  （N 越大，越多的"失败"归因于世界 churn 而非模型）。

---

## 六、这个数**没有**回答什么

写在最后，免得它变成第四个被推翻的分母。

1. **Δ/C 是逐次决策的【直接】覆写率，不是世界级反事实。**
   它没有"关掉模型重跑一局再比两局差异"。前面的覆写会改变世界态，后面的候选集因此不同——
   真正的世界级反事实需要成对重放，代价高一个量级，本轮没做。
2. **等待期这条影响通道完全没数进去。** 模型思考时 `decide()` 返回 `{"_wait": true}`，
   Sim 直接 `return` ⇒ 那几个 tick 该 agent **什么也不做**（`option` 保持 null）。
   等待占比不小（N=12 GPU 下 5453 次调用里 2835 次是 `_wait`）。
   **开着模型的小镇比不开的更"迟疑"**，这件事 Δ/C 量不到。
3. **Δ 不区分"更好"和"更差"。** 覆写率只说"变了"。第四节的效用落差是本轮唯一的质量信号，它是负的。
4. **全是桌面数字。** 真机（8Elite）解码更慢 ⇒ L/C 更低 ⇒ Δ/C 只会**更低**。
   docs/34 那次真机 L/C ≈ 2%，按本文 Δ/L ≈ 89% 折算，**真机 Δ/C ≈ 1.8%**，扣抖动地板后更低。
5. **单模型、单 prompt、单量化。** Δ/L 与四条判据是 `qwen2.5-1.5B-q4_k_m` + 当前闭集选号 prompt 的性质，
   **不是"端上 SLM"的普遍性质**。换更大的模型 / 改 prompt / 把 score 也喂给模型，都可能改变结论——本轮都没测。
6. **候选集规模的混淆没有单独拆。** N=60 的 mean|C| 是 22.3，N=12 是 11.2，随机基线因此不同
   （92.8% vs 88.1%）；本文已按配置分别计算基线，但"候选集变大本身如何影响模型选择质量"没有做单独实验。

## 七、复现

```bash
# 三个配置（出货节奏；每个约 10.3 分钟）
godot --headless --path game res://bench/BackendBench.tscn -- \
  --backend slm --gpu --agents 12 --seeds 1-4 --days 8 --realtime --model <绝对路径>.gguf
#   --cpu 换 CPU 解码；--agents 60 换 cast

# 复读机对照（标定量具 + 测抖动地板），必须与被测配置同 N
godot --headless --path game res://bench/BackendBench.tscn -- --backend mock --agents 12 --seeds 1-4 --days 8

# 确定性 A/B（影子基线开/关，比 event_digest）
godot --headless --path game res://bench/BackendBench.tscn -- --backend mock --agents 12 --seeds 1-4 --days 8 [--no-shadow]
```

**跑并行会毁掉数据**：本轮第一次测量作废重来，原因是被中止的 bench 留下了脱管的 `godot.exe` 子进程，
三个 matrix 并发抢 GPU 并写同一个输出文件（单个文件里出现 2–3 份汇总）。
复现时请确认开跑前没有存活的 `godot.exe`，并检查每个输出文件**有且仅有一份**"汇总"。
